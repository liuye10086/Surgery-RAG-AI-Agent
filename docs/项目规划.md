# Surgery RAG AI Agent — 项目规划

## 1. 项目背景

### 1.1 痛点

通用大模型（如 ChatGPT、DeepSeek 通用版）在医疗垂直领域存在明显不足：
- **知识分散**：医学知识专业性强，通用模型回答不够深入。
- **幻觉风险高**：可能给出看似合理但缺乏依据的医疗建议。
- **来源不可追溯**：无法告诉用户答案来自哪份指南、哪份病历、哪台手术记录。

### 1.2 机会

外科/手术领域存在大量结构化程度高的专业资料：
- 医学指南与操作规范
- 手术记录与病例分析
- 主任专家经验笔记

通过 RAG + Agent 技术，可以构建一个**基于私有知识库、可验证来源、严格受限回答范围**的手术问诊助手。

---

## 2. 项目愿景与目标

### 2.1 一句话愿景

构建面向外科/手术领域的垂直 RAG AI Agent，让医生、医学生和患者都能获得**有依据、可验证、安全合规**的专业医疗知识服务。

### 2.2 发展阶段

| 阶段 | 目标 | 形态 |
|------|------|------|
| **Phase 1：MVP** | 验证 RAG 在手术领域的可行性 | 本地/内网可运行的 Web Demo |
| **Phase 2：内部工具** | 在医院/科室内部小范围使用 | 内网部署，管理员上传资料 |
| **Phase 3：对外服务** | 面向医生、医学生、患者提供付费服务 | 阿里云生产部署 |

> **当前状态（2026-07-22）**：MVP 开发已完成 🎉。Milestone 0–7 全部完成，RAG 全链路（检索 → 生成 → 流式 → 引用 → 审计）已跑通，安全合规（内容过滤 + 危险症状 + 数据导出/删除）已接入，DEPLOY.md 部署手册已编写，内网 Demo 已可运行。

### 2.3 本期目标（MVP）

完成一个最小可行 Demo：
- 支持多轮对话问答
- 基于上传的医学资料回答
- 每个回答附带来源引用
- 知识库不足时明确提示
- 显示医疗免责声明

## 3. 目标用户与核心场景

### 3.1 用户画像

| 用户 | 核心诉求 | 典型问题 |
|------|---------|---------|
| 外科医生 | 快速查指南、查病例、查手术技巧 | “胆囊切除术如何避免损伤胆总管？” |
| 医学生 | 学习手术知识、理解病例 | “急性阑尾炎的手术指征有哪些？” |
| 医院管理人员 | 知识库管理、质量把控 | 上传院内规范、查看使用记录 |
| 患者 | 初步了解疾病和手术 | “我最近下腹痛，可能是什么病？” |
| 科研人员 | 检索文献与案例 | 查找某种术式的并发症统计数据 |

### 3.2 核心场景示例

**场景一：患者问诊**
> 用户：我最近下腹痛，可能是什么病？
> 系统：根据知识库，您最可能是胆囊炎。依据：…（引用病历/指南）

**场景二：医生查手术要点**
> 用户：胆囊切除术如何避免损伤胆总管？
> 系统：…（引用张主任某年某月手术记录、李主任病例分析）

## 4. 核心需求

### 4.1 功能性需求

- 用户注册、登录、角色区分
- 多轮对话问答
- 基于知识库的引用回答
- 文档上传与管理（管理员）
- 会话历史查看
- 审计日志记录

### 4.2 非功能性需求

- **准确性**：回答必须有知识库依据，可验证
- **安全性**：医疗建议必须带免责声明，危险症状优先提示就医
- **合规性**：符合个保法、数据安全法、网络安全法
- **可解释性**：展示答案来源
- **响应速度**：普通问答 3 分钟内完成

### 4.3 成功指标

| 指标 | MVP 目标 |
|------|---------|
| 回答准确率 | ≥ 90%（经医学专家评估） |
| 引用命中率 | 回答中 80% 以上有明确来源 |
| 用户满意度 | 内测用户评分 ≥ 4/5 |
| 知识库覆盖率 | 覆盖核心外科常见病与手术 |

## 5. 项目范围与阶段规划

### 5.1 MVP 范围摘要

**做**：
- Web 聊天界面（Vue 3）
- FastAPI 后端
- PDF / Word / 图片文档入库
- PostgreSQL + pgvector 向量检索
- DeepSeek API 生成答案
- 多轮记忆、引用、免责声明
- 基础审计日志

**不做**：
- 视频解析
- 复杂 Agent / 工具调用
- 真实病历数据（脱敏完成前不上传）
- 生产级部署与负载均衡
- 自动化评估框架

### 5.2 已完成的 Milestone 1–2 关键交付

| Milestone | 目标 | 状态 |
| ------ | ------ | ------ |
| M1：认证与基础 API | JWT 登录/注册、会话/消息 CRUD、健康检查 | ✅ 已完成 |
| M2A：文档上传与分块 | 上传 PDF/DOCX/图片、解析、清洗、分块、状态跟踪、分块预览与单块删除 | ✅ 已完成 |
| M2B：Embedding 与入库 | bge-m3 生成 1024 维向量、写入 pgvector、文档状态流转、重新向量化 | ✅ 已完成 |
| M3：RAG 与 DeepSeek | 混合检索（向量+全文+RRF）、LCEL 链、流式 SSE、引用解析、阈值判断、LangChain 适配器 | ✅ 已完成 |
| M3-modify：LangChain 官方化 | `langchain-postgres` PGVector + `RunnableWithMessageHistory`，自动历史管理 | ✅ 已完成 |
| M4：聊天界面与记忆 | 流式展示、引用卡片、来源面板、侧边栏、欢迎页、多轮记忆（6轮）、加载动画 | ✅ 已完成 |
| M5：安全与审计 | 内容安全过滤（越狱+危险症状+输出过滤）、数据导出/删除 API、Settings 页面、DEPLOY.md | ✅ 已完成 |
| M6：内网 Demo 与试用 | 本地/内网完整运行，邀请目标用户试用，收集反馈 | ✅ 已完成 |
| M7：医学专家评估 | 50–100 条 Q&A 评测集，专家评分 + 迭代优化 | ✅ 已完成 |

实际执行中与最初规划的差异：

- **M2 拆成两步**：先实现上传+分块（M2A），审查分块质量后再做向量化（M2B）。
- **分块策略升级**：从固定滑动窗口 → 段落感知 → 章节标题感知 → 病历级感知（尽量把”病例 1”等完整病历作为单一块）。
- **WPS docx 兼容**：自动清理 WPS 生成的非法关系（`Target=”NULL”`）。
- **模型下载策略**：优先 ModelScope 国内镜像，失败再回退 HuggingFace，并跳过 `.safetensors` 减少下载体积。
- **脚本与上传目录位置**：`scripts/` 与 `uploads/` 放在项目根目录，而非 `backend/` 下。
- **M3 实现方式演进**：M3 先采用自定义 LangChain 适配器（`SurgeryEmbeddings`、`SurgeryRetriever`、`SurgeryChatMessageHistory`、`AuditCallbackHandler`）复用现有 schema；M3-modify 随后升级为 `langchain-postgres` PGVector + `RunnableWithMessageHistory` 官方方案（使用 `langchain-postgres` 而非已弃用的 `langchain-community` PGVector）。
- **M3 与 M4 实际并行交付**：聊天 UI（M4）与 RAG 后端（M3）同步开发，均已完成。
- **引用格式变更**：Prompt 要求模型使用 1-based 序号 `[1]` 而非 `[chunk_id]`，后端 `parse_citations` 按上下文序号映射回实际 chunk。
- **查询改写升级**：从纯规则模板升级为规则 + LLM 双层策略。
- **M5 内容过滤方式**：采用纯规则匹配（正则 + JSON 关键词），不走 LLM；危险症状检测不阻断提问，前端内嵌红色/黄色警告卡片。

### 5.3 完整项目阶段

```
MVP 开发 → 内网 Demo → 医学专家评估 → 迭代优化 → 内部工具化 → 数据脱敏完善 → 阿里云部署 → 对外服务
```

详细 MVP 开发计划见：[MVP开发计划.md](MVP开发计划.md)

## 6. 关键决策

| 决策项 | 选择 | 说明 |
| ------ | ------ | ------ |
| Web 前端 | Vue 3 + Vite + TypeScript + Element Plus | 开发者已掌握 Vue；未引入 Tailwind CSS，UI 全部使用 Element Plus |
| 后端框架 | FastAPI + Pydantic v2 | Python 生态，适合快速开发 |
| ORM | SQLAlchemy 1.x 声明式风格 | 当前代码使用 `Column(...)` 声明式；原计划 2.0 风格未采用 |
| 数据库迁移 | Alembic | `backend/alembic/` 完整管理当前全部业务表和数据库扩展；`schema.sql` 为与最新 head 对齐的参考快照，旧版 SQL 仅作历史资料 |
| 数据库 | PostgreSQL 18.1 + pgvector | 用户已安装，关系数据与向量存储一体 |
| 大模型 | DeepSeek API | 用户指定 |
| Embedding | BAAI/bge-m3（本地） | 中英双语医学检索效果好；通过 ModelScope 国内镜像优先下载，失败回退 HuggingFace |
| 分块策略 | 章节标题感知 + 病历级感知 | 检测到“病例 1 / 案例 1 / Case 1”时尽量把一例完整病历作为单一块，上限 1500 字符 |
| 文档存储 | 本地文件系统 | MVP 阶段不上 OSS；上传目录为项目根目录 `uploads/` |
| 脚本位置 | `scripts/` 在项目根目录 | 验证脚本、检查脚本与代码解耦，删了不影响运行 |
| 数据策略 | MVP 只用匿名/公开资料 | 真实病历待脱敏流程完善后再接入 |
| 部署策略 | 项目后期再上云 | MVP 只做到本地/内网 Demo |
| 初始规模 | 50–200 人 Demo | 1000 并发作为远期目标 |
| 第一个管理员 | 部署脚本创建 | 普通注册用户始终为 `user`；部署人员运行 `python scripts/create_admin.py` 创建管理员 |

## 7. 角色与权限

系统设两类角色：

| 角色 | 权限 | 禁止操作 |
|------|------|----------|
| **普通用户** | 登录、多轮问答、查看自己的历史、导出自己的数据 | 上传文档、查看他人数据、查看审计日志、管理用户 |
| **管理员** | 普通用户全部权限 + 上传/管理知识库文档 + 查看审计日志 + 管理用户 | 做出最终医疗诊断决策 |

说明：

- 普通注册用户固定为 `user`；管理员由部署人员运行 `python scripts/create_admin.py` 创建。
- 后续管理员由现有管理员授予。
- 所有管理员操作写入审计日志。

## 8. 风险与应对（高层）

| 风险 | 影响 | 应对策略 |
| ------ | ------ | ------ |
| 医疗回答幻觉 | 极高 | 强制基于知识库回答、要求引用、不足时明确说明、固定免责声明 |
| 敏感数据泄露 | 极高 | MVP 不上传真实病历、加密存储与传输、审计日志、访问控制 |
| 单人团队瓶颈 | 高 | 严格 MVP 范围、优先跑通核心流程、延后非必要功能 |
| 检索质量不足 | 高 | 混合检索 + 医学专家评估迭代 |
| 合规与责任 | 高 | 内网先行、对外发布前咨询法务、明确免责声明 |
| WPS 生成 docx 解析失败 | 中 | 自动清理 `Target="NULL"` 关系；提供 `scripts/check_documents.py` 上传前检查 |
| bge-m3 模型下载慢/失败 | 中 | 优先 ModelScope 国内镜像，跳过 safetensors，回退 HuggingFace；用户按需开代理 |
| 大文档向量化前端超时 | 低 | `indexDocument` 单独设置 5 分钟超时，并给出友好提示 |
