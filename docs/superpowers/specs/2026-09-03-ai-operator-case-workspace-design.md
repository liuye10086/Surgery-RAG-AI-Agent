# AI 操作者建立病例与病例工作区生产级设计

日期：2026-09-03

状态：用户已确认设计，已完成书面规格自查，待用户复核

## 1. 背景与核查结论

本设计对应 `docs/AI操作者流程核查.md` 第 1 项“操作者建立病例”。核查基线为
`main` 分支提交 `f944a32`。

附录 12 项实施后，第 1 项原记录中的部分缺口已经解决：

- 新病例年龄已要求为 `0–120` 的整数，并已进入数据库、报告输入快照和模型特征链路；
- AI 操作者只能选择已启用且后端已注册能力的 `fatty_liver` 或 `ad`；
- 新病例由后端生成不可变的 `CASE-XXXX-XXXX` 匿名病例编号；
- 病例仍按操作者账号隔离；
- 病例创建已要求携带至少 1 次初始访视，并与病例原子保存；
- 病例状态、疾病停用、输入快照、报告终态和病例删除后的历史报告边界已经建立。

仍需解决的缺口：

- 性别和基线阶段仍可为空，基线阶段在病例保存时没有执行疾病专属的严格校验；
- 点击“保存病例”后仍立即生成报告，病例保存和报告生成没有分离；
- 保存按钮的 loading 只覆盖 Vue 事件派发，不等待真实后端请求；
- 操作者端同时存在 `operator_cases` 纵向病例和 `case_records` 参考病例两套“病例库”，职责混淆；
- 病例资料和访视分别请求保存时可能出现半成功；
- 病例资料和访视更正缺少通用不可变审计记录；
- 创建请求缺少幂等保护，网络重试可能产生重复病例；
- 现有前端测试主要是源码契约测试，缺少组件级和“页面到真实 API、真实 PostgreSQL”的完整验收。

现有相关专项测试在设计前复核时通过：后端 `70 passed, 5 warnings`；所运行的前端年龄、
阶段、病例同步、访视完整性、匿名编号、疾病许可、删除和报告契约测试全部通过。这些结果说明
现有行为稳定，但不代表上述生产缺口已经解决。

## 2. 目标

建立一套唯一、清晰、可审计且可安全重试的 AI 操作者病例工作流：

```text
我的病例
→ 新建病例
→ 填写疾病、年龄、性别和确定的基线阶段
→ 录入至少 1 次初始访视
→ 原子保存病例、初始访视、审计和幂等结果
→ 返回匿名病例编号并停留在病例详情
→ 继续维护资料和访视
→ 达到活动模型要求后，由操作者单独生成报告
```

本设计必须保证：

1. 病例没有至少 1 次有效访视时不能创建或保存；
2. 年龄、性别和确定的疾病专属基线阶段是新病例必填项；
3. 保存病例不会自动生成报告；
4. 一个“保存修改”操作要么全部成功，要么全部回滚；
5. 创建请求可安全重试而不会生成重复病例；
6. 病例和访视的实际更正可追溯；
7. 当前操作者只能访问自己的纵向病例；
8. 历史报告继续读取生成时快照，不随当前病例变化；
9. 操作者端不再维护模型参考病例 `case_records`；
10. 报告生成条件由后端统一计算，前端不硬编码模型门槛。

## 3. 已确认的产品决策

- 保留附录第 5 项的 `1–10` 次访视不变量，不允许零访视病例。
- 病例创建必须包含首次访视；“建立病例”是病例资料和首次访视的一次原子创建。
- 基线阶段必须选择确定值，不提供“待评估”或“不明确”占位值。
- 创建成功后停留在病例详情页，不返回列表，也不自动生成报告。
- 病例保存后可继续添加访视，并提供独立的“生成报告”操作。
- 允许更正年龄、性别、基线阶段、备注和访视，但必须填写变更原因并写不可变审计。
- 历史病例缺少必填字段时不自动推测、不批量回填；保持可读，补齐后才允许其他修改或生成新报告。
- 不增加乐观锁；并发编辑采用后保存覆盖先保存，审计记录保留每次实际修改。
- 创建病例使用幂等键，避免超时或重试导致重复病例。
- 操作者的“病例库”统一为其本人拥有的 `operator_cases`。
- `case_records` 继续作为模型参考数据，但退出 AI 操作者页面和操作者 CRUD API。
- 前端采用单页面病例工作区，不新增多路由分步向导。
- 工作区的“保存修改”使用一个聚合接口，在同一事务内保存病例资料、完整访视时间线和审计记录。

## 4. 信息架构与界面

### 4.1 唯一病例入口

AI 操作者侧边栏保留“新建病例”和“我的病例”。“我的病例”只展示当前用户拥有的
`operator_cases`，不再展示或修改 `case_records`。

列表支持：

- 按匿名病例编号查询；
- 按疾病过滤；
- 按 `active`、`archived` 状态过滤；
- 服务端分页；
- 显示匿名编号、疾病、状态、访视次数和最近更新时间。

列表查询始终包含 `user_id = current_user.id` 所有权条件。不存在和无权访问统一返回 `404`，不能
通过 ID、筛选或错误信息枚举其他操作者的病例。

### 4.2 病例工作区组件

工作区按职责拆分：

- `OperatorCaseWorkspace`：当前病例、创建/详情模式、未保存状态和跨组件编排；
- `OperatorCaseList`：本人病例列表、搜索、筛选和分页；
- `OperatorCaseProfileForm`：疾病、年龄、性别、基线阶段和备注；
- `OperatorVisitTimelineEditor`：首次访视与后续完整时间线编辑；
- `OperatorCaseActionBar`：保存、添加访视、报告就绪状态和生成报告；
- `CaseChangeReasonDialog`：更正已有病例时收集必填变更原因。

每个组件只通过明确的 props、事件和类型化数据交换，不直接调用其他组件内部状态。

### 4.3 新建状态

新建页同时展示病例资料和“首次访视”。以下内容完整且通过前端校验后才能提交：

- 疾病；
- 年龄；
- 性别；
- 确定的疾病专属基线阶段；
- 首次访视日期；
- 至少一个指标、有限数值和合法单位。

匿名编号区域显示“创建后由系统生成”，不得提供可编辑的患者姓名、住院号或自由标签字段。

### 4.4 创建成功状态

创建成功后：

- 页面切换为已保存病例详情；
- 展示后端生成的匿名病例编号；
- 疾病变为只读；
- 显示“病例已保存”；
- 保留刚保存的首次访视；
- 提供“继续添加访视”；
- 展示后端返回的报告就绪原因；
- 不触发报告生成。

### 4.5 修改状态

年龄、性别、基线阶段、备注和访视可以更正。疾病创建后不可修改。只有页面存在实际变化且全部
字段合法时，“保存修改”才可用。

操作者点击“保存修改”后必须输入 `1–500` 个字符的变更原因。前端随后只发送一个聚合保存请求。
请求成功前保持 loading，并禁用重复保存、病例切换和报告生成。

保存失败时保留全部本地输入，并把可定位的校验错误显示在对应字段或访视；全局错误显示在操作区。
切换病例、新建病例或离开页面时，若存在未保存修改，必须确认是否放弃。

### 4.6 报告操作

“生成报告”与“保存病例”是两个独立动作。前端根据后端返回的就绪结果显示按钮状态和具体阻断
原因。生成报告期间病例编辑区只读，避免操作者把尚未保存的页面内容误认为本次报告输入。

### 4.7 视觉与可访问性

实现必须遵循 `docs/DESIGN_SPEC.md`：

- 暖杏蓝配色和已有 CSS 变量；
- 展开侧边栏 `260px`、折叠侧边栏 `64px`；
- 顶部栏 `56px`；
- 主内容最大宽度 `880px`；
- 卡片圆角 `12px`，输入框圆角 `10px`；
- 主要操作最小高度和点击区域 `44px`；
- 错误和状态不能只依赖颜色表达；
- 完整键盘导航、可见焦点和语义化标签；
- 遵循 `prefers-reduced-motion`。

## 5. 请求契约

所有请求模型使用 `extra="forbid"`，防止旧客户端或恶意客户端提交未声明字段并被静默忽略。

### 5.1 创建病例

```http
POST /api/v1/operator/longitudinal-cases
Idempotency-Key: <UUID>
```

请求体：

```json
{
  "disease_id": 1,
  "age": 56,
  "sex": "male",
  "baseline_stage": "pre_cirrhosis",
  "notes": null,
  "visits": [
    {
      "visit_date": "2026-09-03",
      "indicators": [
        {"name": "alt", "value": 42, "unit": "U/L"}
      ],
      "notes": null
    }
  ]
}
```

`patient_label`、`anonymous_case_code`、`status`、`user_id` 和 `visit_index` 均不得由客户端提交。

纵向病例的新增、列表和详情响应不再输出历史 `patient_label`。该数据库列仅作为旧数据兼容字段保留，
不能通过 AI 操作者 API 或前端重新暴露；前端 `LongitudinalCase` 类型也移除该字段。

后端在一个事务中完成疾病许可、病例字段、阶段、访视、指标和幂等校验，随后写入病例、访视、
创建审计和幂等完成结果。任一步失败，事务全部回滚。

### 5.2 聚合保存病例

```http
PUT /api/v1/operator/longitudinal-cases/{case_id}
```

请求体：

```json
{
  "age": 57,
  "sex": "male",
  "baseline_stage": "pre_cirrhosis",
  "notes": "定期复核",
  "visits": [
    {
      "visit_date": "2026-09-03",
      "indicators": [
        {"name": "alt", "value": 42, "unit": "U/L"}
      ],
      "notes": null
    }
  ],
  "change_reason": "更正年龄并补充备注"
}
```

聚合保存遵循后保存覆盖先保存，不提交或校验版本号。后端对病例行加写锁，重新验证状态和疾病许可，
在同一事务内保存资料、重建或更新完整访视时间线、生成字段级差异并写一条审计记录。疾病 ID 和
匿名编号不得修改。

无实际变化的请求返回当前病例，不写审计记录。存在实际变化但 `change_reason` 缺失或仅含空白时
返回 `422`。

现有单访视新增、修改、删除和整体替换接口可以保留以兼容已有内部调用，但病例工作区不再组合
调用这些接口完成一次页面保存。所有保留的写接口仍必须执行状态、疾病、所有权和审计规则。

### 5.3 报告就绪查询

```http
GET /api/v1/operator/longitudinal-cases/{case_id}/report-readiness
```

响应至少包含：

```json
{
  "ready": false,
  "case_ready": true,
  "timeline_ready": false,
  "model_ready": true,
  "visit_count": 2,
  "minimum_visits": 3,
  "blockers": [
    {
      "code": "insufficient_visits",
      "message": "当前有 2 次有效访视，活动模型至少需要 3 次"
    }
  ]
}
```

`minimum_visits` 必须从当前活动模型组关联的数据清单读取，当前值为 `3`；前端不得硬编码。报告
创建接口在数据库写入 `generating` 报告之前重新执行同一就绪校验，避免绕过前端或状态在查询后
发生变化。

`model_ready` 复用第 4 项“调用当前疾病模型”的活动模型和环境安全边界。本设计不改变合成演示
模型的临床有效性声明，也不将 `production_enabled=false` 的模型表述为生产临床模型。

### 5.4 病例列表

现有列表接口增加匿名编号查询、疾病、状态、`skip` 和 `limit` 参数，返回总数和当前页。默认按
`updated_at DESC, id DESC` 稳定排序。所有筛选都在所有权条件之后组合，不能返回其他操作者数据。

### 5.5 参考病例接口退出

删除 AI 操作者路由中的以下 `case_records` 接口及其前端调用：

- `POST /api/v1/operator/cases`；
- `GET /api/v1/operator/cases`；
- `PUT /api/v1/operator/cases/{case_id}`；
- `DELETE /api/v1/operator/cases/{case_id}`。

`case_records` 表、受控导入脚本和后端相似病例检索继续保留。本设计不新增 AI 操作者访问参考病例
明细的替代接口。

## 6. 领域校验

### 6.1 新病例必填

- `disease_id`：正整数且对应已启用、已注册能力的疾病；
- `age`：严格整数，范围 `0–120`；
- `sex`：只允许 `male` 或 `female`，不能为空；
- `baseline_stage`：非空、规范化后属于当前疾病；
- `visits`：`1–10` 次；
- 每次访视：日期和 `1–30` 个指标；
- 每个指标：标准代码、有限数值和该疾病指标允许的标准单位。

脂肪肝允许的阶段为：

- `pre_cirrhosis`；
- `suspected_cirrhosis`；
- `cirrhosis`；
- `hcc`。

AD 允许的阶段为：

- `normal`；
- `mci`；
- `pre_dementia`；
- `dementia`。

病例创建和修改使用统一阶段校验服务。客户端只能发送稳定英文代码，中文仅用于显示。

### 6.2 访视不变量

- 一个病例始终保留 `1–10` 次访视；
- 同一病例不能有重复访视日期；
- 后端按日期排序并生成连续的 `visit_index = 1..N`；
- 客户端不能提交 `visit_index`；
- 指标继续使用统一疾病指标校验服务；
- 整体保存失败时保留原病例和原访视，不产生部分更新。

### 6.3 历史病例兼容

数据库中的年龄、性别和基线阶段继续允许历史 `NULL`，避免为旧病例写入推测值。读取接口继续输出
这些空值，前端明确列出缺失字段。

活动旧病例可以通过一次聚合保存补齐缺失项；本次保存必须同时满足当前全部不变量并写审计。旧病例
未补齐前不得执行其他资料或访视修改，也不得生成新报告。归档或疾病停用病例继续保持只读。

## 7. 数据库设计

新增一个 Alembic revision，衔接当前 head `0019`。迁移必须同步 ORM、`database/schema.sql` 和只读
数据库检查脚本。

### 7.1 性别约束

为 `operator_cases.sex` 增加命名检查约束：

```sql
sex IS NULL OR sex IN ('male', 'female')
```

字段暂不改为 `NOT NULL`，以兼容历史空值。新建和聚合保存的必填性由请求和服务层保证。

基线阶段具有疾病依赖，不使用数据库触发器跨表验证。数据库保留可空字符串列，新的在线写入由统一
阶段服务保证稳定代码和疾病匹配。

### 7.2 病例变更审计表

新增 `operator_case_change_logs`：

- `id`：主键；
- `case_id`：可空外键，删除病例时 `ON DELETE SET NULL`；
- `case_id_snapshot`：不可空病例 ID 快照；
- `anonymous_case_code_snapshot`：匿名编号快照；
- `actor_id`：可空操作者外键，账号删除时 `ON DELETE SET NULL`；
- `actor_id_snapshot`：不可空操作者 ID 快照；
- `action`：`created`、`profile_updated`、`timeline_updated`、`case_updated` 或 `deleted`；
- `reason`：创建记录使用固定系统原因，用户修改记录保存必填原因；
- `changes`：JSONB 字段级差异，只保存实际变化，不复制整份病例；
- `created_at`：不可空服务器时间。

审计表只通过内部服务写入。本次不为 AI 操作者提供审计查询或删除接口。审计记录与业务修改使用同一
事务；审计写入失败时业务修改也回滚。病例删除后的审计记录保留，但不能用于重建或修改历史报告。

### 7.3 幂等请求表

新增 `operator_idempotency_keys`：

- `id`：主键；
- `user_id`：不可空操作者外键，账号删除时 `ON DELETE CASCADE`；
- `scope`：首版固定为 `create_longitudinal_case`；
- `idempotency_key`：客户端生成的 UUID；
- `request_sha256`：规范化请求体摘要；
- `resource_type`：首版固定为 `operator_case`；
- `resource_id`：创建成功后的病例 ID 快照，不建立病例外键，避免病例删除时丢失幂等历史；
- `created_at`：服务器时间。

`(user_id, scope, idempotency_key)` 建立唯一约束。请求摘要在 Pydantic 校验和文本规范化后，使用键递归
排序、UTF-8 无空白 JSON 和 SHA-256 生成；访视顺序在计算前按日期规范化。幂等表不保存请求正文、
指标值或患者资料。相同键和相同摘要返回第一次创建结果；相同键但不同摘要返回
`409 idempotency_key_reused`。如果原病例已经删除，同一键重放返回
`409 idempotency_resource_missing`，不得重新创建病例。首次事务失败时不留下成功幂等记录，客户端
可以使用同一键重试。

## 8. 服务边界与事务

后端至少形成以下职责清晰的单元：

- 病例字段校验：年龄、性别、必填状态和不可变字段；
- 阶段校验：标准化并验证疾病专属阶段；
- 访视校验：数量、日期、排序、序号和指标契约；
- 病例命令服务：创建和聚合保存事务；
- 差异服务：生成稳定、最小化的资料和访视变化；
- 审计服务：构建并写入不可变变更记录；
- 幂等服务：规范化请求、计算摘要和处理重复请求；
- 报告就绪服务：病例、时间线和活动模型条件；
- 病例查询服务：所有权过滤、搜索、筛选和分页。

接口层只负责鉴权、请求解析、错误映射和响应输出，不直接拼装跨表写事务。

创建事务：

```text
解析并严格校验请求
→ 获取并验证幂等键
→ 验证疾病许可、阶段和访视
→ 生成匿名编号
→ 写入病例和初始访视
→ 写入 created 审计
→ 写入幂等完成记录
→ commit
```

聚合保存事务：

```text
按 user_id 和 case_id 查询并锁定病例
→ 验证 active 状态与疾病许可
→ 验证完整资料和完整访视时间线
→ 计算字段与访视差异
→ 无变化则返回
→ 保存资料和访视
→ 写入一条聚合审计
→ commit
```

不增加乐观锁或版本字段。数据库行锁只用于保证单个事务内部一致性；两个先后完成的有效请求采用
后完成结果覆盖先完成结果。

## 9. 错误语义

- `400`：缺少、格式错误或不支持的 `Idempotency-Key`；
- `404`：病例不存在或不属于当前操作者；
- `409`：病例已归档、疾病停用、重复访视日期、访视数量冲突或幂等键内容冲突；
- `422`：年龄、性别、阶段、指标、单位、数值、变更原因或请求字段不合法；
- `503`：活动模型或报告服务暂时不可用。

错误响应包含稳定错误代码和可操作的中文信息。不得向客户端返回数据库语句、路径、堆栈、模型内部
名称、密钥或其他操作者数据。

普通日志只记录内部病例 ID、操作者 ID、接口动作、耗时和稳定错误代码；不记录完整临床资料、指标值、
匿名编号全文、请求体、审计差异或可能的身份信息。

## 10. 报告就绪与历史稳定性

就绪结果分为：

- `case_ready`：病例年龄、性别、阶段、状态和疾病许可通过；
- `timeline_ready`：访视内容通过且数量达到活动模型数据清单的 `minimum_visits`；
- `model_ready`：当前疾病活动模型组满足既有模型安全边界；
- `ready`：上述三项全部为真。

病例最低保存数量仍为 1，报告最低访视数量当前为 3，两者不得混为同一个规则。

报告生成时只读取数据库中已提交的病例和访视，构建新的不可变输入快照。页面未保存的修改不进入
报告。已有报告正文、预测结果、输入快照、来源、匿名编号和完整性字段均不因当前病例更正而变化。

## 11. 测试与验收

### 11.1 后端单元测试

- 创建 Schema 拒绝缺失或空的性别、阶段和初始访视；
- 创建 Schema 拒绝 `patient_label`、匿名编号、状态和客户端访视序号；
- 纵向病例响应和前端类型不暴露历史 `patient_label`；
- 两个病种分别接受自己的阶段并拒绝跨病种阶段；
- 聚合保存要求 `1–10` 次访视和必填变更原因；
- 无变化保存不写审计；
- 资料、访视和混合修改生成正确的最小差异；
- 报告就绪从活动数据清单读取最少访视数；
- 旧病例缺失字段时得到稳定阻断原因。

### 11.2 数据库与迁移测试

- Alembic 只有一个 head，新 revision 正确衔接 `0019`；
- 性别约束允许历史 `NULL`，拒绝其他非法值；
- 审计和幂等表字段、索引、唯一约束和外键删除语义正确；
- ORM、Alembic、`database/schema.sql` 和只读检查器一致；
- upgrade 和 downgrade 不修改病例、访视或历史报告内容；
- 迁移前只读检查报告非法历史性别和不完整病例数量，但不自动修改。

### 11.3 API 集成测试

使用独立 PostgreSQL 测试数据库和真实 FastAPI 请求覆盖：

- 病例、初始访视、创建审计和幂等结果一次提交；
- 任一写入失败时四者全部回滚；
- 相同操作者、scope、幂等键和请求返回同一病例；
- 相同键对应不同请求返回 `409`；
- 不同操作者可使用相同 UUID，且数据仍互相隔离；
- 聚合保存资料和访视全部成功或全部回滚；
- 归档、停用、越权和非法阶段不能绕过；
- 1、2 次访视可以保存但报告未就绪，达到 3 次后按活动清单重新计算；
- 报告创建接口独立复核就绪状态；
- 历史报告不因病例修改而改变。

### 11.4 前端组件测试

引入 Vitest、Vue Test Utils 和合适的 DOM 测试环境，覆盖：

- 必填字段和首次访视校验；
- 创建时生成并复用同一幂等键直到本次提交结束；
- 保存 loading 等待真实 Promise；
- 保存成功后停留在详情且不调用报告接口；
- 更正资料要求变更原因；
- 保存错误保留输入并定位错误；
- 未保存修改离开保护；
- 疾病创建后只读；
- 就绪原因由 API 数据渲染，不硬编码数字；
- 生成期间编辑区只读；
- 列表只使用纵向病例 API，不再引用 `case_records` API。

### 11.5 浏览器端到端测试

使用 Playwright 和独立测试数据库覆盖脂肪肝与 AD：

```text
操作者登录
→ 新建病例
→ 填写完整资料和首次访视
→ 保存
→ 验证匿名编号和详情页
→ 验证没有自动生成报告
→ 添加第 2、3 次访视并填写变更原因
→ 验证报告按钮从阻断变为可用
→ 生成报告
→ 验证病例、访视、审计、报告和输入快照均已落库
```

另使用第二个操作者账号验证列表、详情、修改、审计相关行为和报告均不能跨账号访问。

## 12. 部署与观测

仓库实施不连接或修改生产数据库。正式发布顺序：

```text
生产数据库备份
→ 执行迁移前只读检查
→ 人工确认历史非法值和不完整病例统计
→ alembic upgrade head
→ 部署后端
→ 部署前端
→ 执行脂肪肝和 AD 冒烟
→ 核对审计、幂等、事务回滚和双操作者隔离
```

应用回滚时不删除已经产生的审计和幂等数据。数据库结构变更保持对旧应用读取路径兼容；若必须执行
downgrade，需先停止写入并备份。

生产监控只记录聚合指标：

- 病例创建成功和失败数量；
- 稳定校验错误代码计数；
- 幂等重放和冲突次数；
- 病例创建及保存耗时；
- 报告就绪阻断原因计数；
- 审计写入失败数量。

监控标签不得包含匿名编号、年龄、性别、阶段、访视日期、指标名称或指标值。
