# 附录十至十二输入快照、报告状态与病例删除设计

## 一、文档目的

本文档针对《AI 操作者流程核查》附录第 10、11、12 项，定义输入快照可追溯性、报告生成状态收敛以及病例删除后的历史报告保留规则。

本设计只覆盖 AI 操作者的纵向预测报告链路，兼容脂肪肝和阿尔茨海默病两条现有疾病链路。本文档是实施前的约束，实施必须先按测试驱动开发编写失败测试，再编写最小实现。

## 二、范围与目标

### 2.1 目标

1. 为新生成报告建立稳定、可验证的输入快照完整性标识和生成批次标识。
2. 使输入快照、预测结果和报告正文能够验证是否属于同一次生成。
3. 防止模型加载、预测、渲染、取消和超时导致报告长期停留在 `generating`。
4. 明确病例删除后历史报告的保留、读取和权限边界。
5. 保持历史数据只读兼容，不批量补写或重算已有报告。

### 2.2 不在范围内

- 不连接、读取、迁移、修改、删除或重写生产数据库数据。
- 不修改附录第 1～9 项的业务规则和实现。
- 不新增报告重试、恢复或重新生成接口。
- 不新增病例软删除状态或独立审计日志表。
- 不改变脂肪肝和阿尔茨海默病现有模型适配器、任务路由和输出语义。
- 不自动清洗、补写或重算历史报告的快照、正文和预测结果。

## 三、当前问题

### 3.1 第 10 项：输入快照不可证明属于哪一批输入

当前报告已保存 `input_snapshot`，但没有数据库级哈希或生成批次编号。报告只能展示快照内容，不能通过稳定摘要证明输入是否被改动，也不能清楚区分同一病例的不同生成尝试。现有预测结果中的模型发布集信息不能替代输入快照完整性标识。

### 3.2 第 11 项：模型加载失败可能留下半成品

当前流程先提交 `generating` 报告，再加载活动模型。模型加载发生在报告生成器统一异常处理之外，加载失败可能使报告长期保持 `generating`。已有生成阶段异常和取消处理不能覆盖模型加载失败、超时及并发终态覆盖等场景。

### 3.3 第 12 项：病例删除后的报告依赖快照但规则不完整

当前报告对病例使用 `ON DELETE SET NULL`，病例删除后报告可以保留，但报告与病例的关联、关系对象中的匿名编号等信息会消失。列表、详情和文件生成必须明确只依赖报告自身保存内容，并继续执行原操作者权限校验。

## 四、方案比较与选型

### 4.1 输入完整性标识

**方案一：仅在快照 JSON 内保存哈希。**

优点是无需增加数据库字段，改动较小。缺点是数据库无法直接查询和索引，快照与哈希可能被同时改写，审计能力不足。

**方案二：独立数据库字段，并在快照内保留声明（采用）。**

独立字段用于查询、审计和一致性检查，快照内声明用于单条报告导出后的自证。两处值必须由服务层校验一致。该方案需要新增数据库字段和 Alembic 迁移，但可验证性和可维护性最好。

**方案三：单一完整生成清单字段。**

优点是字段数量少，缺点是查询、约束和审计工具复杂，不能清晰区分输入哈希、批次和失败阶段。

### 4.2 报告生成状态

**方案一：先加载模型，成功后创建报告。**

实现简单，但模型加载失败没有报告级审计记录。

**方案二：先创建报告，再由统一状态机收敛（采用）。**

保留生成尝试记录，模型加载、特征处理、预测和渲染失败均可安全落到终态，审计能力最好。

**方案三：轻量预检查后创建，再由状态机兜底。**

可减少常见失败，但会增加重复加载、预检查与正式加载之间的不一致风险，实现复杂度更高。

### 4.3 病例删除规则

**方案一：有历史报告即禁止删除病例。**

追溯简单，但病例生命周期会被报告永久阻塞。

**方案二：病例软删除。**

追溯完整，但需要新增状态、删除时间和所有查询隔离规则。

**方案三：硬删除病例、保留报告并解除关联（采用）。**

与现有 `ON DELETE SET NULL` 一致，报告依靠不可变快照独立保存，范围适中且不会引入新的病例生命周期。

## 五、数据模型设计

### 5.1 `ai_reports` 新增字段

新增以下四个可空字段，以兼容历史报告：

| 字段 | 类型建议 | 用途 | 新报告要求 |
| --- | --- | --- | --- |
| `input_snapshot_sha256` | `String(64)` | 输入快照规范化后的 SHA-256 | 创建时必须写入 |
| `generation_batch_id` | `String(36)` | 单次生成尝试的唯一批次编号 | 创建时必须写入 |
| `generation_fingerprint` | `String(64)` | 绑定快照、预测结果和正文的完整指纹 | 成功完成时必须写入 |
| `error_stage` | `String(50)` | 固定失败阶段代码 | 失败或取消时写入 |

字段均允许为空，避免对既有历史行执行批量回填。新报告创建后，前三项中的前两项必须存在；报告完成后完整指纹必须存在；失败和取消报告必须记录安全阶段代码。

本次需要新增一条 Alembic 迁移，并同步更新 SQLAlchemy 模型和字段契约测试。迁移只改变表结构，不触碰既有报告数据内容。

### 5.2 输入快照内容

快照继续以现有隐私受限结构为基础，包含疾病稳定代码、生成时匿名病例编号、年龄、性别、基线阶段、按日期和业务顺序排列的访视、指标、备注及模型选项。

快照增加以下元信息：

- `canonicalization_version: "v1"`
- `hash_algorithm: "sha256"`
- `input_snapshot_sha256: 64 位小写十六进制字符串`

不将操作者身份、数据库自增编号、当前时间、文件路径、密钥或其他非业务易变字段纳入哈希输入。病例编号属于生成时展示所需的匿名标识；不得通过哈希反推其他操作者或病例。

## 六、快照规范化与哈希规则

### 6.1 规范化规则

建立无副作用的纯函数，将快照转换为稳定 JSON 字节：

1. 字典对象按键名递归排序。
2. 列表保持生成时的业务顺序，不进行无依据排序。
3. 日期统一为 `YYYY-MM-DD` 字符串。
4. 数字使用稳定的 JSON 表示，不依赖本地化格式。
5. 使用 UTF-8 编码和无额外空白的 JSON 表示。
6. 哈希声明字段本身不纳入哈希输入，避免循环依赖。

### 6.2 输入快照哈希

对去除哈希声明后的规范化快照字节计算 SHA-256，输出小写十六进制字符串。计算结果同时写入 `ai_reports.input_snapshot_sha256` 和 `input_snapshot.input_snapshot_sha256`。

### 6.3 完整生成指纹

完整指纹对带字段名的结构化对象计算 SHA-256，结构包含：

- 规范化输入快照；
- 规范化 `prediction_result`；
- 报告正文的 UTF-8 字节摘要。

不直接拼接无边界字符串，避免字段边界歧义。正文本身不重复存入指纹对象，只保存正文摘要后参与计算。验证时重新计算并同时检查输入快照哈希、快照内声明、数据库独立字段和完整生成指纹。

如果任一摘要缺失或不一致，报告只显示“历史完整性标识不可验证”，不得自动修复、重算或覆盖历史内容。

## 七、报告状态机

### 7.1 状态集合

报告生成状态限定为：

- `generating`：正在生成；
- `completed`：生成、持久化均成功；
- `failed`：发生模型加载、特征、预测、渲染、持久化或超时失败；
- `cancelled`：用户主动取消或流式连接取消。

### 7.2 状态转换

```text
generating
├── completed  模型加载、特征、预测、渲染和持久化全部成功
├── failed     模型加载失败、运行异常、持久化异常或超时
└── cancelled  用户主动取消或流式连接取消
```

终态不可再次转换。已进入终态的报告不能被重复请求覆盖。

### 7.3 失败阶段

`error_stage` 只允许固定值：`model_loading`、`feature_extraction`、`prediction`、`rendering`、`persistence`、`timeout`、`cancelled`。对外只返回通俗中文提示；日志只记录报告编号、批次编号、稳定错误码和阶段，不记录异常原文、路径、密钥或敏感输入。

## 八、事务边界与并发控制

### 8.1 创建事务

创建报告使用短事务：锁定并读取当前操作者拥有且处于可生成状态的病例，完成疾病、年龄、访视和指标校验，构造快照，计算哈希，生成批次编号，插入 `generating` 报告后提交。任一环节失败则整体回滚，不留下报告记录。

### 8.2 生成与完成事务

模型加载、特征提取、预测和正文渲染不占用数据库长事务。成功时使用条件更新：仅当报告仍为 `generating` 才同时写入预测结果、正文、来源、完整指纹并改为 `completed`。失败、取消和超时也使用相同条件更新，写入安全错误码与阶段后提交。

条件更新未影响任何行时，说明其他并发流程已完成状态转换，当前流程不得覆盖结果，也不得再次写入错误。

### 8.3 幂等性

每次报告生成尝试拥有独立 `generation_batch_id`。同一报告只允许一次终态提交；不新增重试接口。用户再次生成时创建新的报告和批次，旧报告保持不可变。

## 九、病例删除与报告读取

### 9.1 删除事务

病例删除继续使用现有硬删除流程：删除病例，访视因外键级联删除，报告的 `operator_case_id` 因 `ON DELETE SET NULL` 置空。删除流程不得删除、更新、重算或回填历史报告。

### 9.2 历史报告保留内容

报告保留生成时的 `input_snapshot`、`prediction_result`、`content`、`sources`、模型发布集信息、完整性字段和生成时匿名病例编号。报告不依赖当前病例关系恢复历史内容。

### 9.3 权限边界

报告列表、详情和 PDF 必须先按 `AIReport.user_id == current_user.id` 校验。病例关系为空不能扩大可见范围，也不能通过报告查询其他操作者的病例。报告展示不得返回原始患者标签、操作者身份、数据库路径或内部异常。

### 9.4 缺失数据降级

旧报告或被删除病例对应的报告若缺少快照、匿名编号、哈希或完整指纹，继续允许安全只读读取，并显示“历史资料不完整”或“历史完整性标识不可验证”。不从当前病例补回缺失内容。

## 十、兼容策略

1. 新增字段全部可空，旧报告不执行批量回填。
2. 旧报告继续支持既有预测结果版本和详情、列表、PDF 只读流程。
3. 旧报告缺少完整性字段时，不参与新的完整性断言，只返回不可验证状态。
4. 新报告必须写入批次编号和输入哈希；成功报告必须写入完整生成指纹。
5. AD 和脂肪肝继续分别使用各自疾病代码、适配器和活动模型组，不共享疾病专属输入规则。

## 十一、接口与错误处理

- 现有创建报告接口继续作为生成入口，不新增重试、恢复或重新生成接口。
- 报告列表只返回必要摘要，不返回完整预测结果和内部错误详情。
- 报告详情可返回快照及完整性验证状态，但不返回敏感内部信息。
- 报告下载只使用已保存正文和预测结果，不重新读取病例或重新预测。
- 模型加载失败对外返回“模型暂时不可用，请稍后重试”，内部记录 `model_loading`。
- 超时对外返回“报告生成超时”，内部记录 `timeout`。
- 取消对外返回“报告生成已取消”，内部记录 `cancelled`。
- 任何异常都必须在响应前完成安全状态收敛；不得把 traceback、密钥、文件路径或敏感输入写入数据库或响应。

## 十二、测试策略

### 12.1 后端单元与契约测试

先编写失败测试，再实现：

1. 快照规范化对对象键顺序、日期、数字和访视顺序具有稳定结果。
2. SHA-256 结果、快照内声明和独立字段一致。
3. 修改快照、预测结果或正文时完整生成指纹验证失败。
4. 新报告创建时写入批次编号和输入哈希。
5. 旧报告字段为空时仍可列表、详情和下载。
6. 模型加载失败进入 `failed`，且阶段为 `model_loading`。
7. 特征、预测、渲染、持久化异常和超时均进入安全终态。
8. 取消和重复终态更新不会覆盖已有终态。
9. 错误响应和错误字段不含 traceback、路径、密钥或敏感输入。
10. 病例删除后报告保留、外键置空、快照和正文可读。
11. 其他操作者不能读取被删除病例对应的历史报告。
12. AD 与脂肪肝各有至少一组成功和失败回归测试。
13. Alembic、ORM、数据库 schema 和 Pydantic 契约字段一致。

### 12.2 前端契约与构建测试

若前端需要展示完整性状态、失败阶段或病例已删除提示，必须先读取并遵守 `docs/DESIGN_SPEC.md`。测试覆盖报告详情字段兼容、安全状态文案、病例关系为空时的降级展示，并运行相关前端契约测试和生产构建。

### 12.3 验收命令

实施完成后至少运行相关后端专项测试、相关前端契约测试、前端构建、Alembic/ORM/schema 一致性检查、`git diff --check` 和 `git status --short --branch`。所有结果必须以实际命令输出为准，不得将仓库测试通过表述为生产环境已上线。

## 十三、生产环境边界与上线前步骤

本设计和后续实施均不连接生产数据库，不执行生产迁移，不读取或改写生产数据。实施完成后，生产环境仍需在独立发布窗口中完成：备份、只读结构核查、确认 Alembic 当前版本、执行迁移、迁移后结构核查、双疾病冒烟和回滚预案验证。未经这些步骤，不得宣称已上线。

## 十四、风险与接受标准

### 14.1 已接受的边界风险

- SHA-256 提供完整性校验，不提供密钥签名和不可抵赖性。
- 旧报告缺少哈希和指纹，只能安全读取，无法追溯到完整生成批次。
- 病例硬删除后，报告只能依据生成时快照还原病例信息，不能恢复当前病例关系。
- 不提供报告级重试接口，失败后需由操作者创建新报告。

### 14.2 完成标准

- 新报告具备批次编号、输入快照哈希和完整生成指纹。
- 模型加载失败、异常、取消和超时均能在有限时间内进入终态。
- 病例删除后历史报告仍按原操作者权限安全读取，且不依赖当前病例。
- 历史数据未被批量补写、重算、清洗或删除。
- AD 和脂肪肝链路专项测试通过，前端契约和构建通过，结构一致性检查通过。
