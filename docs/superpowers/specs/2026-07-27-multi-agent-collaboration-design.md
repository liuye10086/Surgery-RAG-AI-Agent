# Codex 与 Claude Code 多角色协作设计

## 1. 目标

在不预设 Codex 与 Claude Code 长期职责的前提下，为项目建立可追踪、可审核、低冲突的协作流程。

本设计需要保证：

- 每项任务均有明确负责人、范围和验收条件。
- Codex 与 Claude Code 可以并行工作，但不能覆盖彼此的未提交修改。
- Git 历史能够区分规划者、实现者、评审者和使用的客户端。
- AI Agent 可以创建本地提交，但推送和合并必须由项目所有者明确批准。
- 高风险修改经过方案确认和交叉评审后才能进入主分支。

## 2. 当前阶段范围

本阶段只建立协作规范、任务登记模板和入口文件引用，不固定两个 Agent 的长期职责，也不创建永久 worktree。

永久 worktree 容易因长期不使用而落后于 `main`。因此，在具体任务被认领后，才为该任务创建独立分支和 worktree；任务结束并合并后再清理。

## 3. 工作区与分支模型

### 3.1 协调工作区

当前项目目录作为协调工作区，保持在 `main`，用于：

- 维护活动任务登记。
- 审核任务方案和代码评审结果。
- 在获得项目所有者批准后推送或合并。

协调工作区不承担并行任务的直接实现，避免任务实现与协调记录混在同一工作树中。

协调工作区由项目所有者控制，不设置永久的“协调 Agent”角色。项目所有者可以明确委托当前 Agent 执行一次性的任务登记、状态更新或审核整理；该委托不扩大 Agent 的权限，也不允许 Agent 自主推送或合并。

### 3.2 任务 worktree

每个实现任务使用独立分支和独立 Git worktree：

- Codex 分支：`codex/<task-id>`
- Claude Code 分支：`claude/<task-id>`

创建任务分支前，协调工作区必须处于干净状态，并按以下顺序同步远程基线：

```powershell
git fetch origin
git switch main
git pull --ff-only origin main
```

如果 `main` 无法快进，必须停止创建任务分支并交由项目所有者处理，不得自动 rebase、强制重置或制造隐式合并提交。同步完成后，任务分支从最新的本地 `main` 创建。

两个 Agent 不得同时操作同一个物理工作目录，也不得认领文件范围重叠的活动任务。

## 4. 任务登记

协调工作区使用 `docs/coordination/ACTIVE_TASKS.md` 作为活动任务的唯一登记源。

每项任务至少记录：

- `Task-ID`
- 任务标题
- 负责人和客户端
- 分支与 worktree 路径
- 具体文件路径、路径模式，以及必要时的函数、类或接口名称
- 风险级别
- 规划要求
- 验收条件
- 当前状态
- 规划者、实现者和评审者

活动任务状态使用：

- `planned`：已登记，尚未开始实现。
- `in-progress`：负责人正在实现。
- `review`：已完成本地提交，等待评审或项目所有者审核。
- `changes-requested`：评审发现需要修复的问题。
- `approved`：已通过所需评审，等待项目所有者批准推送或合并。
- `blocked`：因依赖、环境、权限或其他无法自行恢复的问题暂停。
- `completed`：已合并到 `main`。
- `cancelled`：任务取消，不再继续。

实施 Agent 不在自己的任务分支中修改 `ACTIVE_TASKS.md`。状态变更由协调工作区统一维护，避免多个任务分支产生重复登记和合并冲突。

任务范围必须尽量使用可比较的具体路径，例如：

```text
Exact files:
- backend/app/api/admin.py
- backend/app/schemas/document.py

Path patterns:
- backend/alembic/versions/*

Symbols:
- backend/app/api/admin.py: upload_document()
```

不以行号作为主要范围边界，因为编辑后行号会漂移。认领任务前必须读取所有非终止状态任务，人工比较具体文件、路径模式、符号范围及数据库等共享资源。仅依赖关键词搜索不能证明没有语义重叠；如范围不明确，应先细化登记或向项目所有者确认。

## 5. 规划分级

### 5.1 微小修改

适用于文案、注释、小范围文档和无行为变化的配置修正。只需在活动任务登记中写清目标、范围和验收条件。

### 5.2 普通任务

适用于常规功能和一般 Bug 修复。任务登记必须包含简短实现说明、影响范围和验证方式，确认后才能实现。

### 5.3 高风险任务

跨模块、数据库迁移、认证授权、安全控制、RAG 核心链路和架构调整属于高风险任务。必须先在 `docs/plans/` 或项目约定的设计目录编写方案，并由项目所有者明确批准后实施。

规划者与实现者可以相同，也可以由 Codex 和 Claude Code 交叉承担；项目不设置永久角色绑定。

## 6. 本地提交与身份留痕

Agent 可以在自己的任务分支创建原子本地提交，但不得自行执行以下操作：

- 推送到远程仓库。
- 合并到 `main`。
- 修改或 amend 另一个 Agent 的提交。
- 强制推送或重写共享历史。

提交主题遵循项目通用格式，例如：

```text
feat(retrieval): optimize hybrid search
```

提交正文必须包含：

```text
AI-Agent: Codex
AI-Client: Codex-Desktop
Task-ID: retrieval-001
```

Claude Code 使用：

```text
AI-Agent: Claude-Code
AI-Client: VS-Code
Task-ID: chat-002
```

如果规划者、实现者或评审者不同，应在任务登记或方案文档中分别记录，不能只依赖 Git author 推断职责。

为避免两个客户端争用仓库级 `user.name` 和 `user.email`，Agent 提交时优先通过单次命令参数设置身份，而不是反复修改仓库配置。

## 7. 评审规则

评审要求按风险决定：

- 普通文档和微小配置修改可由项目所有者直接审核。
- 功能、Bug 修复、数据库、认证、安全和 RAG 核心逻辑必须由另一个 Agent 交叉评审。

评审 Agent 只输出问题、证据、风险和测试缺口，不直接修改实现者的提交。需要修复时，由原实现者创建新的本地提交，保留完整审查轨迹。

Codex Desktop 与 VS Code 中的 Claude Code 是彼此独立的客户端，默认不能互相唤起。需要交叉评审时，由项目所有者在另一个客户端发起评审；实现 Agent 必须主动提醒项目所有者，并生成可直接粘贴的标准评审交接信息，至少包含 `Task-ID`、实现者、评审者、分支、基线、提交范围、方案或任务登记路径、验收条件、重点检查项，以及“只输出评审意见，不直接修改实现提交”的要求。

如果评审者是同一客户端内部、且项目所有者明确允许使用的子 Agent，可由当前 Agent 调度；这不等同于 Codex 与 Claude Code 的跨客户端交叉评审，不能替代设计中明确指定的另一个客户端评审者。

评审完成后，协调工作区更新任务状态。任务满足所需评审和验证后，实现 Agent 必须主动报告分支、提交、变更范围和验证结果，并明确提示“尚未推送”，请求项目所有者授权。只有项目所有者可以批准推送和合并。

本项目由单人所有者管理时，批准可以是一条明确指令，例如“允许推送 `retrieval-001`”或“允许合并 `retrieval-001` 到 `main`”，不要求额外审批系统或表单。推送与合并是两个独立授权；“实现完成”“检查通过”或“可以了”等表述不自动视为授权。该规则的目的只是区分“Agent 完成工作”和“项目所有者授权改变远程或主分支状态”。

## 8. UI 专项规则

任何 UI 修改开始前，负责 Agent 必须完整读取 `docs/DESIGN_SPEC.md`，并遵守其中的色彩、排版、间距、圆角、阴影、动效、组件变体、布局尺寸和医生/患者双角色规范。

除非项目所有者明确要求改变视觉风格，否则不得偏离该设计规范。

## 9. 标准任务流程

1. 项目所有者在 `main` 登记任务，或明确委托当前 Agent 代为执行一次登记，分配唯一 `Task-ID`、负责人、范围和风险级别。
2. 检查现有活动任务，确认文件范围不存在重叠。
3. 根据风险级别完成必要规划，并取得项目所有者批准。
4. 确认协调工作区干净，执行 `git fetch origin` 和 `git pull --ff-only origin main`，再从最新本地 `main` 创建任务分支和独立 worktree。
5. 负责人只在任务 worktree 中实现和验证，创建带身份尾注的原子本地提交。
6. 普通或高风险代码需要另一个 Agent 评审时，实现 Agent 主动提醒项目所有者并生成标准交接信息；项目所有者在另一个客户端发起评审。微小修改可由项目所有者直接审核。
7. 原实现者针对评审意见创建后续提交，不改写已有提交。
8. 任务通过评审和验证后，实现 Agent 报告本地状态并主动请求推送授权；项目所有者明确授权后才可推送。
9. 推送完成后，实现 Agent 报告远程状态并单独请求合并授权；项目所有者明确授权后才可合并到 `main`。
10. 合并后将任务标记为 `completed`，再清理任务 worktree 和分支。

## 10. 冲突与异常处理

- 如果两个任务范围重叠，后登记任务必须等待、拆分范围或重新分配，不能同时实现。
- 如果实现中发现必须越出登记范围，先暂停修改并更新任务登记，经确认后继续。
- 如果 `main` 在任务期间发生变化，负责人应先评估差异，再以非破坏方式同步；不得通过强制重置丢弃修改。
- 如果任务涉及数据库 schema 或迁移链变更，必须在登记中显式标注。默认同一时间只允许一个活动任务修改 schema 或 Alembic revision 链；确需并行时，必须预先确定 revision 依赖和合并顺序，后登记任务基于已确定的前置 revision 更新迁移，不得各自假设自己是最新 migration head。
- 如果评审者认为需求或实现方案存在歧义，应停止进入合并阶段并向项目所有者澄清。
- 如果 Agent 遇到无法自行恢复的依赖缺失、环境问题、权限限制或执行中断，应停止扩大修改范围，将任务标记为 `blocked`，记录阻塞原因、已完成内容和未验证项目，由项目所有者决定修复环境、重新分配、继续或取消。
- 如果验证环境不完整，任务记录必须明确未执行的测试及原因，不能宣称验证通过。

## 11. 落地文件

实施阶段将新增或修改：

- `AI_COLLABORATION.md`：所有 Agent 必须遵循的共享协作规范。
- `docs/coordination/ACTIVE_TASKS.md`：活动任务登记表。
- `docs/coordination/TASK_TEMPLATE.md`：任务登记模板和字段说明。
- `AGENTS.md`：保留现有项目概述、UI 规则和通用规则，在文件顶部新增强制读取共享规范的入口。
- `CLAUDE.md`：保留现有项目概述、UI 规则和通用规则，在文件顶部新增强制读取共享规范的入口。

两个入口文件新增的提示采用相同含义：开始任何项目操作前，必须先阅读并遵守 `AI_COLLABORATION.md`。现有 UI 规范引用统一使用实际路径 `docs/DESIGN_SPEC.md`。

当前阶段不增加自动化任务锁、Git hooks 或 GitHub Issues 强制流程。待轻量流程实际运行后，再根据冲突频率决定是否引入自动化。

## 12. 验收标准

- Codex 与 Claude Code 的入口文件都明确引用同一份共享规范。
- 活动任务模板能够记录负责人、范围、风险、规划、验收和状态。
- 活动任务范围使用具体路径、路径模式和必要的符号名称，而不是依赖不稳定的行号。
- 文档明确禁止 Agent 未经批准推送或合并。
- 文档明确要求独立 worktree 和非重叠任务范围。
- 文档明确任务分支创建前的远程同步与非快进停止规则。
- 文档能够区分规划者、实现者和评审者，而不固定长期职责。
- 文档明确高风险任务的方案审批与交叉评审要求。
- 文档明确跨客户端评审由项目所有者发起，实现 Agent 主动提醒并生成标准交接信息。
- 文档明确实现 Agent 在本地完成后主动请求推送授权，且推送与合并分开授权。
- 文档明确数据库迁移串行协调和 Agent 阻塞处理方式。
- UI 修改规则继续指向 `docs/DESIGN_SPEC.md`。
