# 独立标准文档上传与版本创建链路设计

## 1. 背景

当前标准规则层已经包含标准集合、标准版本、解析片段、候选规则、审核、发布和兼容投影，但标准版本的原始文件仍通过 `reference_standard_versions.document_id` 引用普通知识库的 `documents` 表。

这造成了错误的领域边界：

- 普通知识库文档需要支持分块、向量化和聊天检索。
- 标准 DOCX 只应进入标准专用解析、审核和发布链路。
- 上传普通文档与创建标准版本是两个没有清晰衔接的操作。
- 管理员上传标准文件后无法明确选择文件、疾病和版本并创建草稿。
- 标准文件可能被误认为需要进入普通知识库处理链路。

本设计将标准原始文件从 `documents` 中彻底分离，建立独立标准文档库，并明确“上传文件”和“手动选择文件创建版本”的两阶段工作流。

## 2. 目标

1. 新增只保存标准源文件的 `standard_documents` 表。
2. 普通知识库文档与标准文档使用互不混用的数据模型和 API。
3. 管理员先上传标准 DOCX，再在标准集合下手动选择文件创建版本。
4. 一个标准文档最多关联一个标准版本，关联后锁定。
5. 标准集合名称固定由疾病名称生成，不允许管理员修改。
6. 保留现有解析、候选、审核、发布、resolver 和纵向报告语义。
7. 不迁移现有 `documents` 数据，不向正式数据库写入测试数据。

## 3. 非目标

- 不把标准片段加入普通 PGVector 集合。
- 不修改纵向预测模型 artifact、特征顺序或训练流程。
- 不改变规则、条件树、候选审核和发布投影的医学语义。
- 不提供标准集合改名或删除功能。
- 不复用同一标准文件创建多个版本。
- 不自动迁移、识别或转换 `documents` 中的历史文件。

## 4. 方案选择

采用独立 `standard_documents` 表，`reference_standard_versions` 直接引用新表。

不采用以下方案：

- 通用 `file_assets` 基表：需要迁移全部普通文档，影响分块、向量化和文件删除，范围过大。
- `documents` 加分类或关联表：标准文件仍属于普通文档，不能真正建立领域隔离。

## 5. 数据模型

### 5.1 `standard_documents`

新增表：

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | integer | PK | 标准文档 ID |
| `title` | varchar(500) | nullable | 管理员填写标题，未填时使用文件名 |
| `filename` | varchar(500) | not null | 原始文件名 |
| `file_path` | varchar(1000) | not null | 服务器保存路径 |
| `file_type` | varchar(50) | not null | 规范化为 `docx` |
| `file_size` | integer | not null | 文件字节数 |
| `content_hash` | varchar(64) | unique, not null | 文件 SHA-256 |
| `uploaded_by` | integer | FK users, SET NULL | 上传管理员 |
| `created_at` | timestamptz | not null | 上传时间 |

表中不持久化 `available` 或 `locked` 状态。锁定状态由是否存在关联的 `reference_standard_versions` 记录实时推导，避免状态与外键关系不一致。

同一内容哈希只能上传一次。修订标准必须上传内容不同的新 DOCX。

### 5.2 `reference_standard_versions`

调整字段：

- 删除 `document_id -> documents.id`。
- 新增 `standard_document_id -> standard_documents.id`。
- `standard_document_id` 为 `NOT NULL`。
- `standard_document_id` 增加唯一约束。
- 外键删除策略为 `RESTRICT`。

唯一约束保证一个标准文档最多关联一个版本。删除允许删除的版本后，该文档自然恢复为可用状态。

ORM 关系改为：

- `ReferenceStandardVersion.standard_document`
- `StandardDocument.version`，`uselist=False`

### 5.3 `reference_standards`

继续保持一个疾病最多一个标准集合的唯一约束。

创建标准集合时仅接收 `disease_id`，名称由后端按 `${disease.name}标准` 生成。名称不通过创建或更新 API 暴露给管理员修改。

## 6. 文件存储边界

标准上传使用独立服务函数，但物理文件保存可以复用现有底层上传能力和 `UPLOAD_DIR`。本次不重构普通文档的保存目录、文件服务或历史文件路径；领域隔离以独立 `standard_documents` 表、独立标准管理员 API 和标准管理页面只调用标准 API 为准。

标准文件必须满足：

- 扩展名为 `.docx`，大小限制复用全局上传限制。
- 保存过程使用安全文件名和唯一前缀。
- 保存后计算 SHA-256，再创建数据库记录。
- 数据库写入失败时删除本次新保存的文件。
- 删除可用标准文档时，先确认无版本关联，再删除磁盘文件和数据库记录。

标准文件不进入普通文档的分块、索引、检索或访问范围逻辑。

## 7. 管理员 API

所有接口继续要求管理员身份。

### 7.1 标准文档

```text
POST   /v1/admin/standard-documents/upload
GET    /v1/admin/standard-documents
DELETE /v1/admin/standard-documents/{document_id}
```

上传接口使用 multipart：

- `file`: 必填 DOCX。
- `title`: 可选。

列表接口默认返回全部标准文档，并返回派生字段：

- `is_locked`
- `standard_id`
- `standard_name`
- `version_id`
- `version_label`

支持 `available_only=true`，供新建版本下拉框只查询未关联文档。

删除接口规则：

- 未关联文档允许删除。
- 已关联任意版本返回 `409`。
- 前端不能仅靠隐藏按钮实现保护，后端必须再次校验。

### 7.2 标准集合

```text
GET  /v1/admin/reference-standards
POST /v1/admin/reference-standards
```

创建请求：

```json
{
  "disease_id": 2
}
```

后端检查疾病存在，并自动生成名称。疾病已有标准集合时返回 `409`。

### 7.3 标准版本

创建版本请求调整为：

```json
{
  "standard_document_id": 12,
  "version_label": "fatty-liver-2026-08"
}
```

创建时依次校验：

1. 标准集合存在。
2. 标准文档存在。
3. 文档是 DOCX 且磁盘文件存在。
4. 文档尚未关联版本。
5. 同一标准不存在相同内容哈希版本。

数据库唯一约束作为并发条件下的最终保护。唯一冲突转换为 `409`，不向客户端暴露数据库异常。

新增：

```text
DELETE /v1/admin/reference-standard-versions/{version_id}
```

删除规则：

- `draft`、`review` 允许删除。
- `approved`、`retired` 返回 `409`。
- 删除版本级联删除片段、候选、规则、条件和变更日志。
- 不删除 `standard_documents`，文档解除锁定并恢复可用。

## 8. 生命周期与删除规则

```text
上传 DOCX
  -> standard_documents（可用）
  -> 管理员选择标准集合
  -> 手动选择文件并填写版本名称
  -> reference_standard_versions（draft）
  -> 文档被唯一外键锁定
  -> 手动解析
  -> 规则与候选审核
  -> submit review
  -> approve
  -> 成为当前发布版本
```

删除矩阵：

| 对象 | 状态 | 是否可删除 | 结果 |
| --- | --- | --- | --- |
| 标准文档 | 未关联 | 是 | 删除磁盘文件和记录 |
| 标准文档 | 已关联 | 否 | `409`，先处理版本 |
| 标准版本 | draft | 是 | 删除版本，文档解锁 |
| 标准版本 | review | 是 | 删除版本，文档解锁 |
| 标准版本 | approved | 否 | 永久保留 |
| 标准版本 | retired | 否 | 永久保留 |
| 标准集合 | 任意 | 否 | 当前不提供删除接口 |

## 9. 管理员页面

页面遵循 `docs/DESIGN_SPEC.md`，继续使用暖杏蓝变量、现有管理员侧边栏和紧凑工作台布局。

### 9.1 标准文档库

顶部提供 DOCX 上传控件和文档表格。

表格显示：

- 标题和文件名
- 内容哈希摘要
- 文件大小和上传时间
- 状态：可用或已关联
- 已关联时的标准名称和版本名称
- 未关联文档的删除操作

已关联文档不显示删除操作；后端仍执行冲突校验。

### 9.2 标准集合

提供“新建标准集合”操作：

- 从现有疾病列表选择疾病。
- 已有标准集合的疾病从选项中排除。
- 页面显示自动生成的名称，不提供名称输入框。
- 创建成功后自动选中新集合。

### 9.3 新建版本

选中标准集合后提供“新建版本”：

- 选择未锁定标准文档。
- 填写版本名称。
- 没有可用文档时按钮禁用，并提示先上传 DOCX。
- 创建成功后刷新文档和版本列表，文档显示已关联，页面自动选中新草稿。
- 创建版本不自动解析，管理员继续手动点击“解析”。

### 9.4 审核工作台

保留现有：

- 版本选择和状态显示
- 解析、提交审核、批准发布和退役
- 原文片段、规则、校验问题和规则修改原因
- 现有候选审核与变更历史后端 API 行为保持不变；本次不新增页面工作台功能

为 `draft`、`review` 版本增加删除操作，并使用确认对话框说明文档将解除锁定、解析结果将删除。

## 10. 错误处理与并发

- 非 DOCX：`422`，说明只支持 DOCX。
- 重复内容哈希：`409`，提示相同内容已上传。
- 文档已被其他请求关联：`409`，前端刷新可用文档列表。
- 删除已关联文档：`409`，提示先删除允许删除的版本。
- 删除批准或退役版本：`409`。
- 疾病不存在：`404`。
- 疾病已有标准集合：`409`。
- 磁盘文件不存在：阻止解析或创建版本，并返回可操作错误。
- 上传数据库事务失败：清理新写入的磁盘文件。
- 磁盘删除失败：不删除数据库记录，返回错误，避免留下不可追踪状态。

## 11. Alembic 迁移

新增 revision `0010`，down revision 为 `0009`。

升级顺序：

1. 检查 `reference_standard_versions` 是否已有记录。
2. 若已有记录，中止迁移并输出需人工处理的明确错误；不转换、不删除数据。
3. 创建 `standard_documents`。
4. 删除 `reference_standard_versions.document_id` 外键和字段。
5. 新增 `standard_document_id`、唯一约束和 `RESTRICT` 外键。
6. 更新相关索引。

本项目确认不迁移 `documents` 中任何记录，新表从空数据开始。

降级规则：

- `standard_documents` 和标准版本均为空时，允许回到 `0009`。
- 已产生标准业务数据时中止降级，防止数据丢失或重新混入普通文档表。
- 验证空库迁移链：`0009 -> 0010 -> 0009 -> 0010`。

## 12. 对现有模块的影响

必须调整：

- 标准 ORM 与 Pydantic schema。
- 管理员标准文档和版本 API。
- 标准专用文件存储封装；可复用现有底层保存能力，但不得改变普通文档文件服务行为。
- 标准解析器入口、生命周期服务和初始化脚本。
- 标准管理前端和 API 类型。
- 所有引用 `version.document`、`document_id` 的标准层测试。

保持不变：

- 普通文档物理保存目录和文件服务行为。
- 普通文档上传、分块和向量化接口。
- `standard_segments`、候选、规则和条件树结构。
- 发布事务和 `reference_ranges` 兼容投影语义。
- resolver 的疾病、上下文和版本选择规则。
- 纵向模型 artifact 和模型输入。

## 13. 测试策略

### 13.1 后端

- 只允许 DOCX 上传。
- 上传成功保存文件、哈希和管理员。
- 相同内容不能重复上传。
- 列表正确推导可用和锁定状态。
- 未关联文档可删除，已关联文档不可删除。
- 创建集合自动命名且疾病唯一。
- 创建版本锁定文件，重复关联在串行和并发条件下均失败。
- 删除 draft/review 版本后文档解锁。
- approved/retired 版本不可删除。
- 解析、候选、审核、发布和 resolver 使用 `standard_document`。
- 普通文档 API 不返回标准文档。

### 13.2 前端

- 标准文档上传和列表只出现在标准管理。
- 可用/已关联状态和删除操作正确。
- 创建集合不提供名称输入框。
- 创建版本只列出可用文档。
- 创建成功刷新两个列表并选中新草稿。
- 删除版本确认和生命周期按钮状态正确。
- 所有控件满足设计规范和键盘可访问性。

### 13.3 真实文件与迁移

- 使用 `AD标准.docx` 和 `脂肪肝标准.docx` 在隔离测试数据库完成上传、建集合、建版本和解析。
- 验证段落、表格、候选和规则来源可追溯。
- 不向正式数据库写入测试记录。
- PostgreSQL 执行 `0009 -> 0010 -> 0009 -> 0010`。
- 运行后端全量测试、前端全量测试和生产构建。

## 14. 验收标准

1. 标准文件不再写入或读取 `documents`。
2. 标准管理页面能看到所有标准文档及其可用/锁定状态。
3. 管理员能够手动选择未锁定文档创建草稿版本。
4. 同一文档不能关联第二个版本。
5. 标准集合名称始终由疾病名称自动生成。
6. 未关联文档可删除，已关联文档受保护。
7. draft/review 版本删除后文档恢复可用。
8. approved/retired 版本和文档不可删除。
9. 两份真实标准 DOCX 能进入现有解析与审核链路。
10. 普通知识库文档链路、纵向预测和报告行为无回归。
11. Alembic 在空标准数据条件下完成升降级验证。
12. 全量测试和前端构建通过。
