# 附录第七项：病例标签匿名保护设计

## 1. 目标与范围

本设计用于完成《docs/AI操作者流程核查.md》附录第 7 项，解决 `patient_label` 可被误填为姓名、住院号、手机号、身份证号、邮箱或其他联系方式的问题。

本次整改覆盖：

- 新建病例、修改病例以及访视保存触发的病例保存路径；
- 报告生成、报告标题、历史报告列表、报告详情和 PDF 下载；
- 输入快照、预测调用边界、日志和 API 错误信息；
- 导入脚本、合成数据和训练数据的兼容处理；
- 历史病例与历史报告的只读兼容；
- 数据库模型、Alembic 迁移、只读检查脚本和专项测试。

本次不做：

- 不连接、读取、迁移或修改生产数据库；
- 不自动清洗、删除或批量改写历史生产数据；
- 不把数据库内部主键直接作为对外病例编号；
- 不修改附录第 1～6 项或其他附录内容；
- 不把“代码已实现”表述为“生产已上线”。

## 2. 已确认的产品决策

### 2.1 操作者不能自定义匿名编号

新病例不再接受操作者输入可自由填写的病例标签。前端不提供可编辑的 `patient_label` 输入框，后端也不信任客户端提交的标签值。

### 2.2 匿名编号必须可读

系统生成的展示编号采用固定格式：

```text
CASE-XXXX-XXXX
```

其中 `X` 为大写字母或数字，排除容易混淆的字符。编号使用随机来源生成，不编码姓名、住院号、手机号、身份证号、邮箱、出生日期、创建日期、病种或数据库主键。

### 2.3 编号创建后不可变

病例创建时生成 `anonymous_case_code`。后续病例修改、访视保存、归档、恢复和报告生成都只能读取该编号，不能重新生成或修改编号。

### 2.4 数据库内部主键与展示编号分离

- `operator_cases.id`：数据库内部主键，只用于内部关联和权限校验；
- `operator_cases.anonymous_case_code`：操作者可见的匿名病例编号，用于病例列表、报告标题、历史列表、PDF 文件名和 PDF 正文病例标识；
- `operator_cases.patient_label`：保留为兼容字段，用于旧数据读取和必要的受控迁移兼容，不作为新病例的对外输出来源。

## 3. 新旧数据兼容策略

### 3.1 新病例

新病例必须拥有系统生成的 `anonymous_case_code`。新写入不接受自由文本 `patient_label`，也不允许客户端覆盖系统生成的编号。

### 3.2 旧病例

旧病例可能没有 `anonymous_case_code`，也可能在 `patient_label` 中保存旧格式或身份信息。系统不得自动清洗或改写旧标签。

旧病例读取时采用以下顺序：

1. 已有 `anonymous_case_code`：使用该编号；
2. 没有匿名编号但存在旧标签：在受控兼容读取中显示旧标签，并标记为“旧标签待治理”，不把它写入新的报告标题、文件名、日志或模型输入；
3. 两者都没有：显示稳定的“旧病例未设置匿名编号”提示，不把数据库主键伪装成匿名编号。

旧报告按已保存的 `content`、`title`、`query`、`input_snapshot` 和 `prediction_result` 原样读取，不因新规则重新生成。历史报告兼容读取不等于历史内容已经完成脱敏。

### 3.3 导入病例

导入脚本继续使用数据集内部的 `patient_id` 维护同一病例分组、访视幂等和训练数据关联，但导入到应用病例表时必须生成独立的 `anonymous_case_code`（或使用数据集明确声明的匿名编号映射）。导入的原始 `patient_label` 不能进入在线报告标题、PDF 文件名、日志或模型输入。

### 3.4 合成训练数据

合成训练数据可以继续保留 `AD-DEMO-001`、`P001` 等数据集标识，用于训练、审计和分组拆分。模型特征不得包含 `patient_label`、`group_id` 或其他身份字段。合成来源必须继续带有合成标记，不能被当作真实患者身份。

## 4. 应用层数据流设计

### 4.1 输入与病例保存

- `OperatorCaseCreate`：移除新病例对自由 `patient_label` 的依赖，创建时由服务层生成 `anonymous_case_code`；为兼容旧客户端，若仍提交 `patient_label`，后端不得将其作为展示编号保存或回显；
- `OperatorCaseUpdate`：不允许修改 `anonymous_case_code`；旧客户端提交的 `patient_label` 只能进入兼容策略，不能覆盖匿名编号；
- 访视新增、修改、删除和整体替换：只修改访视数据，不重新生成病例编号；
- 归档、恢复和删除：沿用现有权限与状态规则，匿名编号保持不可变；删除病例不自动删除历史报告数据，历史报告仍按已有报告权限规则读取。

### 4.2 报告生成

报告生成时构造独立的展示标识和模型输入：

- `report.title`：`{anonymous_case_code}纵向进展预测报告`；
- `report.query`：使用匿名病例编号或固定的内部报告查询标识，不使用原始旧标签；
- `input_snapshot`：保存 `anonymous_case_code`、病例和访视必要结构化数据，不保存新病例的自由身份标签；
- 模型特征：只传年龄、性别、基线阶段和指标等已定义特征，不传 `patient_label` 或 `anonymous_case_code`；
- 报告正文：病例标识只使用匿名病例编号；相似病例来源只展示其匿名来源编号和合成/真实来源状态，不展示原始自由标签。

### 4.3 报告历史与详情

历史报告列表和详情接口统一使用匿名病例编号作为展示字段。接口不能因为客户端传入任意 `report_id` 或标签而透露其他操作者的报告存在性；继续沿用当前按用户归属返回 404 的权限策略。

### 4.4 PDF

- PDF 标题和正文病例标识使用 `anonymous_case_code`；
- `Content-Disposition` 的 ASCII 回退文件名使用 `report-{report_id}.pdf`；
- UTF-8 文件名使用匿名病例编号生成，不使用原始旧标签或旧报告标题中的敏感内容；
- 历史报告下载不重新生成历史预测，只按已保存报告内容生成兼容 PDF；若历史标题含旧敏感标签，下载层应采用安全匿名文件名，并在文档中说明历史正文仍需单独治理。

### 4.5 日志与错误信息

- 普通应用日志只记录 `case_id`、`report_id`、稳定错误码和阶段信息；
- 日志不记录 `patient_label`、请求原文中的自由标签或完整快照；
- API 错误返回通俗中文和稳定错误码，不回显被拒绝的敏感标签；
- 审计日志如需关联病例，只保存内部 ID 或匿名病例编号，不保存自由身份文本。

## 5. 编号生成与唯一性

系统在服务层集中提供匿名编号生成函数，生成 `CASE-XXXX-XXXX` 格式的候选值，并通过数据库唯一约束和冲突重试保证唯一。

编号生成要求：

- 使用密码学安全随机源或项目现有安全随机工具；
- 字符集固定，排除 `I`、`O`、`1`、`0` 等易混淆字符；
- 不包含用户 ID、病例 ID、时间戳、病种代码或可逆编码；
- 生成失败或唯一性冲突时阻断病例创建，不降级为数据库主键或自由标签；
- 匿名编号写入后不可更新。

## 6. 数据库与迁移策略

新增 `operator_cases.anonymous_case_code` 字段，长度足以容纳固定格式，初始允许为空以兼容历史病例；新增唯一索引或唯一约束，保护非空编号不得重复。

迁移采用“先加字段、后由应用为新写入生成”的保守策略：

- 不在迁移中批量生成或改写历史编号；
- 不在迁移中扫描、清洗或删除 `patient_label`；
- 不阻断旧病例读取；
- 只读检查脚本增加匿名编号字段、格式、重复和空值统计；
- 若未来需要为历史病例补编号，必须另行设计只读盘点、人工确认和可回滚批处理，本次不执行。

数据库约束能够保护：

- 匿名编号格式（若使用数据库 CHECK）；
- 编号非空（仅适用于完成回填后的新数据或单独约束范围）；
- 编号唯一；
- 病例、报告和用户之间的外键关系。

数据库约束不能保护：

- 旧 `patient_label` 是否包含真实身份；
- 标签是否进入日志、模型输入、报告正文或历史文件名；
- API 是否错误回显敏感文本；
- 历史报告内容是否已经脱敏。

本次不新增触发器、复杂加密方案或依赖数据库函数的随机编号逻辑。

## 7. 错误提示与前端策略

前端病例编辑器不再显示可编辑的自由标签输入框，改为显示“系统自动生成的匿名病例编号（创建后不可修改）”。创建成功后显示编号；编辑、访视保存、归档和恢复页面保持同一编号。

后端拒绝旧客户端自由标签时，返回通俗中文，例如：

```text
病例编号由系统自动生成，不能手动填写；请删除自定义编号后重新保存。
```

错误信息不包含被拒绝的原始内容。前端不能显示“已脱敏”而继续保存原始标签。

前端修改前必须先读取并遵守 `docs/DESIGN_SPEC.md`；本设计不改变既有暖杏蓝视觉体系、布局尺寸和组件交互规范。

## 8. 测试设计

专项测试必须覆盖：

1. 空标签和全空格旧请求的处理；
2. 姓名、住院号、手机号、身份证号、邮箱和联系方式形式的旧请求不会进入新写入；
3. 新病例自动生成可读且符合格式的匿名编号；
4. 编号重复时重试或阻断，不产生重复数据；
5. 病例修改、访视保存、归档和恢复不会改变编号；
6. 报告标题、历史列表、详情、PDF 文件名和 PDF 正文只使用匿名编号；
7. `input_snapshot` 保存约定的匿名病例编号，不保存自由身份标签；
8. 模型输入和预测结果不包含病例身份字段；
9. 日志和 API 错误不泄露原始敏感内容；
10. 历史病例和历史报告仍可读取，且不会自动重新生成；
11. 导入脚本非法标签会被拒绝或隔离，合成训练数据保持兼容；
12. `fatty_liver` 与 `ad` 行为一致；
13. 未登录用户及其他操作者不能通过标签推测报告存在性；
14. 旧数据为空标签或旧格式标签时只读兼容，不自动改写。

测试顺序严格采用 TDD：先写失败测试并确认失败原因是缺少匿名保护，再写最小实现，最后运行相关后端、脚本、前端契约测试和前端构建。

## 9. 验证完成标准

只有同时满足以下条件，才能在文档中写“仓库实现完成”：

- 新病例不再依赖操作者自由填写病例标签；
- 后端生成并持久化唯一、可读、不可变的匿名病例编号；
- 报告标题、历史列表、PDF、日志、快照和模型输入均遵守匿名边界；
- 历史病例和历史报告可兼容读取，未自动清洗或改写；
- 数据库迁移脚本、只读检查脚本和 ORM 契约一致；
- 新增专项测试及相关回归测试全部通过；
- 明确记录生产数据库未连接、未迁移、未修改；
- `git diff --check` 通过且没有无关文件变化。

“仓库实现完成”只代表代码、测试和文档已完成，不代表生产环境已经部署或上线。
