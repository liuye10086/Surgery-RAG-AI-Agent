# AI 操作者疾病许可与稳定代码设计

## 1. 背景

当前 `diseases` 是全局疾病字典，AI 操作者纵向病例通过
`operator_cases.disease_id` 关联疾病。现有纵向病例页面只按中文名称显示“脂肪肝”和
“阿尔茨海默病”，但病例创建和更新接口只验证疾病 ID 是否存在。因此，直接调用接口可以创建
其他疾病的操作者病例，真正的两病种判断直到报告生成时才发生。

此外，模型路由和前端阶段选项依赖中文疾病名称。AI 操作者目前还能新增、修改和删除疾病，修改
名称可能使已有病例无法进入模型路由；删除疾病时，`operator_cases` 当前使用级联删除外键，也
存在误删病例的风险。

本设计只处理疾病身份、AI 操作者许可、病例疾病不可变、停用只读、删除保护和既有数据迁移。
指标字典、病例状态、访视数量等其他数据库附录问题不在本次范围内。

## 2. 已确认的业务边界

- `diseases` 继续作为可扩展的全局疾病字典。
- 项目近期只允许脂肪肝和阿尔茨海默病进入 AI 操作者纵向流程。
- 疾病字典仅管理员可写；AI 操作者只读。
- 疾病具有不可修改的稳定代码，中文名称只用于显示。
- 疾病停用时不删除数据，既有病例和历史报告进入只读状态；重新启用后恢复使用。
- 迁移采用严格识别：当前数据库必须只有两种预期疾病，出现第三种疾病或名称异常即停止迁移。
- 管理员以后新建疾病时必须填写稳定代码，新疾病默认不允许 AI 操作者使用。
- 只有程序已经具备对应能力的疾病才允许启用。
- 疾病一旦被病例、报告或标准引用，就不能物理删除，只能停用。
- 操作者病例创建后不能更换疾病。
- AI 操作者工作台移除疾病字典写入口，疾病维护移到管理员端。

## 3. 方案选择

采用在 `diseases` 增加稳定 `code` 和 `operator_enabled` 字段的方案。

未采用以下方案：

- 不在数据库 CHECK 中硬编码中文疾病名称或环境相关疾病 ID，因为名称可修改、ID 在不同数据库
  不稳定，而且每次扩展疾病都需要修改约束。
- 不在 `operator_cases` 再复制疾病 code，因为会与 `disease_id` 形成重复身份并产生一致性风险。
- 当前不新增疾病许可关联表。现阶段只有一个 AI 操作者纵向许可开关，单独关联表会增加不必要的
  表和接口复杂度；未来出现多租户、多工作流或审批需求时可以再升级。
- 不只使用后端写死白名单，因为管理员需要启停疾病，且停用行为不应依赖重新部署代码。

## 4. 总体架构

每种疾病包含三个核心信息：

| 信息 | 示例 | 作用 |
| --- | --- | --- |
| 稳定代码 | `fatty_liver` | 供模型、阶段和指标配置识别；创建后不可修改 |
| 显示名称 | 脂肪肝 | 页面展示；管理员可以修改 |
| 操作者开关 | 开启/关闭 | 决定当前是否允许进入 AI 操作者纵向流程 |

疾病必须同时满足以下条件才能用于新建病例、写入访视和生成报告：

```text
diseases.operator_enabled = true
且
diseases.code 存在于后端疾病能力注册表
```

职责分配：

- 数据库负责稳定代码、唯一性、启停状态、引用完整性和删除保护。
- 后端疾病能力注册表负责确认该代码是否具备阶段、指标、模型和报告处理能力。
- 管理员负责创建疾病、修改显示信息、启停和安全删除。
- AI 操作者只能读取当前许可疾病，并维护自己的病例。
- 前端按稳定代码选择疾病专属阶段和指标配置，不再按中文名称判断。
- `operator_cases` 继续只保存 `disease_id`，不重复保存稳定代码。

## 5. 数据库设计

### 5.1 `diseases` 新字段

增加：

```text
code VARCHAR(64) NOT NULL
operator_enabled BOOLEAN NOT NULL DEFAULT FALSE
```

约束：

- `code` 全局唯一。
- `code` 只允许小写英文字母、数字和下划线，并且必须以小写英文字母开头。
- `operator_enabled` 不允许为空，新增疾病默认关闭。
- 具体疾病名称和代码取值不写入数据库 CHECK。

当前两种疾病的目标值：

| 显示名称 | 稳定代码 | 操作者状态 |
| --- | --- | --- |
| 脂肪肝 | `fatty_liver` | 开启 |
| 阿尔茨海默病 | `ad` | 开启 |

### 5.2 稳定代码不可修改

管理员创建疾病时必须提交唯一稳定代码。创建成功后，普通更新接口不接受 `code` 字段；管理员
只能修改显示名称和描述。

数据库不会通过触发器阻止拥有直接数据库写权限的运维人员修改代码。直接数据库写入属于受控
运维边界；在线业务必须通过后端接口。生产变更稳定代码需要单独的数据迁移设计，不属于普通
疾病编辑。

### 5.3 操作者病例疾病不可修改

- `OperatorCaseCreate` 保留必填 `disease_id`。
- `OperatorCaseUpdate` 移除 `disease_id`。
- 后端服务不再处理病例疾病变更。
- 旧客户端即使提交 `disease_id`，也必须被请求契约拒绝，不能静默忽略。
- 选错疾病时重新创建病例；原病例按现有删除规则处理，但疾病停用时病例为只读，不能删除。

### 5.4 删除保护

将以下疾病外键统一改为 `ON DELETE RESTRICT`：

- `operator_cases.disease_id`：原来为 `ON DELETE CASCADE`；
- `case_records.disease_id`：原来为 `ON DELETE CASCADE`；
- `ai_reports.disease_id`：原来为 `ON DELETE SET NULL`。

`reference_standards.disease_id` 已经是 `ON DELETE RESTRICT`，保持不变。

管理员删除疾病前，后端显式检查以下引用：

- `operator_cases`
- `case_records`
- `ai_reports`
- `reference_standards` 及其版本化标准数据

只要存在任一引用，删除请求返回冲突错误；管理员只能关闭 `operator_enabled`。只有从未被任何
业务数据引用的空疾病记录可以物理删除。

数据库外键作为最终防线，避免检查与删除之间的并发竞争导致数据丢失。

## 6. 后端设计

### 6.1 统一疾病能力注册表

建立单一后端注册入口，以稳定代码为键，至少能判断：

- 是否存在纵向进展 adapter；
- 是否存在阶段配置；
- 是否存在指标配置；
- 是否允许加载该疾病的模型和报告流程。

首版注册 `fatty_liver` 和 `ad`。现有按中文名称映射 dataset 的逻辑改为读取
`case.disease.code`。

### 6.2 统一许可检查

建立可复用的疾病许可服务。不同接口不得分别维护自己的疾病白名单。

许可服务按 `disease_id` 读取疾病，并区分：

- 疾病不存在；
- 疾病已停用；
- 稳定代码没有程序能力；
- 疾病可用。

以下路径必须使用统一检查：

- 管理员启用疾病；
- AI 操作者获取可用疾病列表；
- 创建操作者病例；
- 新增、替换、修改或删除访视；
- 修改或删除病例；
- 生成新报告。

读取病例、读取历史报告和下载历史 PDF 不受停用限制。

### 6.3 疾病管理权限

- 疾病的新增、修改、启停和删除接口改为仅管理员可调用。
- AI 操作者保留只读的“可用疾病列表”接口。
- 标准管理和参考病例管理如需全量疾病列表，使用管理员权限下的全量疾病接口，不复用操作者许可
  列表。

### 6.4 启用规则

管理员将 `operator_enabled` 从关闭改为开启时，后端必须先验证稳定代码存在于疾病能力注册表。

若能力不存在：

- 不修改数据库开关；
- 返回明确错误“该疾病尚未配置预测能力，不能启用”。

管理员关闭疾病不需要模型检查。关闭操作只改变使用状态，不修改或删除病例、访视、报告和标准。

### 6.5 停用后的只读边界

疾病停用后允许：

- 列出和查看既有病例；
- 查看历史报告；
- 下载历史 PDF。

疾病停用后禁止：

- 新建该疾病病例；
- 修改或删除既有病例；
- 新增、替换、修改或删除访视；
- 生成新报告。

疾病重新启用且程序能力仍然存在后，上述写操作恢复。

### 6.6 API 错误语义

使用稳定中文错误，不向前端暴露 adapter、dataset 或注册表内部名称：

- “该疾病未开放 AI 操作者使用”
- “该疾病尚未配置预测能力，不能启用”
- “病例创建后不能修改疾病”
- “该疾病已停用，病例当前只读”
- “该疾病已被业务数据引用，不能删除”

不存在与无权访问仍按现有安全边界处理，不能借错误信息泄露其他操作者的病例。

## 7. 前端设计

### 7.1 AI 操作者端

- 从病例库页面移除疾病字典的新增、改名和删除区域。
- 疾病选择使用后端返回的“已启用且程序支持”的列表。
- 阶段和指标配置按 `code` 选择，不再比较中文名称。
- 病例编辑器不提供更换疾病的入口；查看既有病例时疾病只读显示。
- 疾病停用时显示“该疾病当前已停用，病例暂时只读”，并禁用病例、访视和报告写操作。
- 前端禁用只是用户体验，后端仍必须独立拒绝绕过请求。

### 7.2 管理员端

增加疾病管理能力：

- 查看全部疾病及固定代码、启停状态和引用状态；
- 新建疾病时填写名称、固定代码和可选描述；新疾病默认关闭；
- 修改名称和描述；固定代码只读；
- 开启或关闭 AI 操作者使用；
- 删除从未被引用的空疾病记录。

启用失败、删除冲突等情况显示后端提供的明确中文原因。

## 8. 严格迁移策略

### 8.1 部署前只读检查

生产升级前的只读检查先区分全新空库和已有数据库。

全新空库必须满足：

- `diseases` 为空；
- 不存在 `operator_cases`、`case_records`、非空疾病引用的 `ai_reports` 或标准数据；
- 当前 Alembic revision 符合升级条件。

已有数据库必须满足：

- `diseases` 中恰好只有两条记录；
- 名称分别精确为“脂肪肝”和“阿尔茨海默病”；
- 所有 `operator_cases`、`case_records`、`ai_reports` 和标准引用都指向这两条疾病；
- 没有孤儿引用；
- 当前 Alembic revision 符合升级条件。

检查失败时停止发布，不执行迁移，不自动修正或删除生产数据。

### 8.2 Alembic upgrade

迁移在一个事务中执行，并先区分两种情况：

- 若疾病字典为空且没有任何疾病相关业务数据，则视为全新空库，自动创建“脂肪肝”和
  “阿尔茨海默病”。
- 若疾病字典非空，则视为已有数据库，必须恰好存在两种预期疾病；不补建缺失疾病，也不识别
  别名。

随后执行：

1. 临时增加可空 `code`。
2. 增加 `operator_enabled BOOLEAN NOT NULL DEFAULT FALSE`。
3. 在迁移内部再次判断空库或已有数据库，防止绕过部署前检查直接运行 Alembic。
4. 对全新空库创建两种基础疾病；对已有数据库检查疾病集合与精确名称。
5. 为“脂肪肝”填写 `fatty_liver`，为“阿尔茨海默病”填写 `ad`。
6. 将两条疾病的 `operator_enabled` 设置为 `TRUE`。
7. 验证所有疾病均已获得代码，且不存在重复代码。
8. 将 `code` 改为非空。
9. 增加 code 唯一约束和格式 CHECK。
10. 将 `operator_cases.disease_id`、`case_records.disease_id` 和 `ai_reports.disease_id`
    外键删除策略改为 `RESTRICT`。

若已有数据库缺少任一预期疾病，或发现第三种疾病、名称异常、无法识别的引用或约束冲突，迁移
抛错并整体回滚。只有完全没有疾病及疾病相关业务数据的全新空库才允许自动创建基础疾病。

迁移不修改病例、访视、报告、标准正文或输入快照。

### 8.3 Downgrade

Downgrade 仅回退本次结构：

- 恢复 `operator_cases.disease_id`、`case_records.disease_id` 和 `ai_reports.disease_id`
  各自原有的外键删除策略；
- 删除 code 格式和唯一约束；
- 删除 `operator_enabled` 和 `code` 字段。

Downgrade 不删除疾病、病例或报告数据。正式生产降级前必须备份并停止新写入。恢复级联删除只是
结构对称要求；降级后仍不得主动删除已有关联病例的疾病。

### 8.4 服务器操作边界

仓库实施阶段只新增迁移、只读检查和部署说明，不连接或修改生产服务器。

正式部署流程：

```text
数据库备份
→ 执行只读检查
→ 人工确认结果
→ alembic upgrade head
→ 启动后端
→ 再次执行只读核对和双疾病冒烟测试
```

## 9. 历史兼容

- 既有 `operator_cases` 继续通过 `disease_id` 关联疾病，无需改写病例行。
- 已保存报告正文、预测结果、来源和 PDF 生成逻辑不重新计算。
- 旧输入快照没有疾病 code 时仍可读取；读取逻辑不能强制要求历史快照包含新字段。
- 新报告输入快照增加生成时疾病 code，同时继续保存疾病 ID 和生成时显示名称。
- 疾病后续改名或停用不改写旧报告快照。

## 10. 测试与验收

### 10.1 数据库和迁移

- 只有两种预期疾病时正确回填 `fatty_liver` 和 `ad`。
- 全新空库自动创建两种基础疾病，填写稳定代码并启用。
- 疾病表为空但存在疾病相关业务数据时迁移失败，不将其误判为可初始化空库。
- 已有数据库缺少任一预期疾病时迁移失败，不自动补建。
- 出现第三种疾病、名称异常或未知引用时迁移失败并完整回滚。
- code 不能为空、不能重复，非法格式被数据库拒绝。
- 迁移前后的疾病、病例、访视、报告和标准数量及关联关系保持不变。
- 已引用疾病无法删除，数据库不会级联删除 `operator_cases`。
- Alembic、ORM、`database/schema.sql` 和只读检查器保持一致。

### 10.2 后端

- AI 操作者不能新增、修改、启停或删除疾病。
- 管理员可以维护疾病，但不能通过普通接口修改稳定代码。
- 未注册程序能力的疾病不能启用。
- 只有已启用且程序支持的疾病可以创建病例。
- 直接调用 API 不能绕过许可。
- 病例创建后不能更换疾病。
- 疾病停用后历史读取正常，所有病例和访视写操作及新报告生成均被拒绝。
- 重新启用后恢复写入。
- 旧报告和缺少疾病 code 的旧快照仍能查看和下载。
- 疾病删除检查覆盖操作者病例、参考病例、报告和标准，并验证并发外键保护。

### 10.3 前端

- AI 操作者端不再出现疾病字典写入口。
- 只能选择后端返回的可用疾病。
- 阶段和指标配置按稳定代码工作，显示名称变化不影响功能。
- 既有病例不允许更换疾病。
- 疾病停用时显示只读提示并禁用相关操作。
- 管理员端正确处理新建、改名、启停和安全删除。
- 后端拒绝操作时显示明确中文原因。

### 10.4 双疾病回归

脂肪肝和 AD 分别完成：

- 病例创建；
- 访视录入；
- 报告生成；
- 历史查看；
- PDF 下载。

同时回归参考病例导入、标准管理、readiness、训练数据构建和模型路由，确认全部改用或兼容稳定
疾病代码，并且两病种不会交叉。

## 11. 实施顺序

1. 为当前可绕过路径和目标权限编写失败测试。
2. 新增严格 Alembic 迁移，并同步 ORM、`schema.sql` 和只读检查器。
3. 建立统一疾病能力注册表和许可服务。
4. 收紧疾病管理权限，增加管理员疾病管理接口和操作者可用疾病接口。
5. 接入病例、访视和报告写入口；移除病例疾病更新能力。
6. 修改 AI 操作者端和管理员端页面。
7. 增加新报告快照 disease code，同时保持旧快照兼容。
8. 运行迁移、后端、前端和双疾病端到端验证。
9. 更新 `docs/AI操作者流程核查.md`，记录本项实际完成情况和验证证据。

## 12. 非目标

本次不处理：

- 为第三种疾病开发模型、阶段或指标适配器；
- 多租户或按角色细分的疾病许可关联表；
- 在线修改稳定代码；
- 自动识别疾病别名或根据病例指标猜测疾病；
- 清理或改写生产病例和历史报告；
- 连接或操作生产服务器。
