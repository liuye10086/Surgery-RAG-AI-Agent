# AI 操作者纵向病例状态生产级约束设计

## 1. 背景与目标

`operator_cases.status` 当前是 `VARCHAR(50) NOT NULL DEFAULT 'active'`。应用层更新请求通过正则只接受
`active` 和 `archived`，但数据库没有合法值约束，内部 ORM 代码和直接 SQL 可以写入任意非空字符串。
同时，现有服务没有集中状态转换规则：归档病例仍可能被修改、写入访视、删除或用于生成新报告，状态变化也没有
专用审计记录。

本设计解决以下问题：

- 数据库最终拒绝非法病例状态；
- 后端使用单一状态定义和集中状态转换服务；
- 明确 `active` 与 `archived` 的业务含义和转换规则；
- 归档病例在 API 和前端均进入只读状态；
- 状态变化具备原因、操作者和时间审计；
- 并发状态修改、病例写入和报告启动不会互相覆盖；
- 既有库迁移不猜测、不自动改写未知状态；
- Alembic、ORM、`database/schema.sql`、只读检查器和测试保持一致。

本文件是仓库设计规格，不表示生产迁移已经执行或上线。本阶段不连接、不读取、不修改生产服务器。

## 2. 当前真实实现

### 2.1 数据库与 ORM

- `backend/app/db/models.py` 将 `OperatorCase.status` 定义为长度 50 的字符串，Python 默认值和服务器默认值均为
  `active`，字段非空。
- `backend/alembic/versions/0008_longitudinal_operator_cases.py` 首次创建该字段时没有 CHECK、ENUM 或状态外键。
- 后续 `0009` 至 `0014` 迁移没有增加病例状态约束。
- `database/schema.sql` 同样只有 `VARCHAR(50) NOT NULL DEFAULT 'active'`。
- ORM、Alembic 和全新安装 SQL 当前均允许数据库直接写入任意非空字符串。

### 2.2 API、Pydantic 与服务

- 新建病例请求不接受状态；`create_operator_case()` 固定写入 `active`。
- 普通病例更新请求 `OperatorCaseUpdate` 当前包含 `status`，正则只接受 `active|archived`。
- `update_operator_case()` 对所有已提交字段执行通用 `setattr()`，没有专用状态服务、转换矩阵或状态审计。
- 病例列表只支持疾病筛选，不支持状态筛选。
- 查询、更新和删除均按当前用户 ID 限制病例所有权；`admin` 通过 `require_ai_operator` 继承操作者能力，仍只能处理
  自己拥有的病例。
- 疾病停用时，现有 `get_operator_case_for_write()` 会阻止病例和访视写操作；读取仍允许。
- 当前状态没有参与病例写入资格判断，因此只要疾病仍启用，`archived` 病例仍可能被修改、删除、写入访视或生成报告。

### 2.3 前端

- TypeScript 类型将纵向病例状态声明为 `'active' | 'archived'`。
- 当前纵向病例选择器只显示患者标签，没有状态标签、状态筛选、归档按钮或恢复按钮。
- 当前病例编辑器只根据疾病是否停用决定只读，不根据病例状态决定只读。
- 普通保存流程不会主动提交状态，但任何客户端都可以绕过界面直接调用更新 API。
- `CaseManageView.vue` 管理的是 `case_records` 参考病例，不是本设计涉及的 `operator_cases`。

### 2.4 脚本、报告、数据集与测试

- 未发现导入、初始化、数据集构建或训练脚本直接写入 `OperatorCase.status`。
- 报告输入快照包含病例身份、疾病、年龄、性别、基线阶段、病例备注和访视，不包含病例状态。
- 病例状态不参与数据集生成、模型训练、模型路由或预测结果。
- 报告使用独立状态集合，如 `generating`、`completed`、`failed`、`cancelled`；不得与病例状态混淆。
- 现有测试使用 `active` 夹具并覆盖部分 Pydantic 校验，但没有数据库状态约束、转换矩阵、归档只读、状态审计、
  状态筛选或并发状态修改测试。
- 现有 `audit_logs` 面向聊天和模型调用，不适合作为病例业务状态审计表。

### 2.5 当前可绕过路径

| 路径 | 当前结果 |
| --- | --- |
| 正常前端 | 没有状态修改入口 |
| 绕过前端直接调用病例更新 API | 未知状态被 Pydantic 拒绝，但 `active` 和 `archived` 可直接互改 |
| 内部代码直接设置 ORM 属性 | 可写任意长度范围内的非空字符串 |
| 直接 SQL INSERT/UPDATE | 可写任意长度范围内的非空字符串 |
| 归档后继续调用资料、访视、删除或报告接口 | 当前服务没有统一按病例状态阻止 |
| 并发归档、恢复和其他病例写入 | 当前没有病例行级串行化，可能基于旧状态继续写入 |

数据库 CHECK 只能保证状态值属于合法集合，不能强制所有直接 SQL 的合法状态转换都产生应用审计。生产业务写入必须
通过后端；直接数据库写入属于受控 DBA/迁移边界。数据库会最终拦截非法字符串，应用层负责合法值之间的转换、原因、
权限和审计。

## 3. 已确认的业务规则

### 3.1 合法状态集合

病例状态只包含两个稳定英文代码：

| 状态代码 | 中文显示 | 业务含义 |
| --- | --- | --- |
| `active` | 使用中 | 可以维护病例资料、维护访视、删除病例和启动新报告 |
| `archived` | 已归档 | 暂时停用但可恢复；仅允许查看病例、访视和历史报告 |

数据库只保存英文代码。中文名称由前端显示映射提供，不写入数据库约束，也不作为业务判断依据。

### 3.2 状态转换矩阵

| 当前状态 | 目标状态 | 结果 |
| --- | --- | --- |
| `active` | `archived` | 允许；必须填写原因并写一条审计记录 |
| `archived` | `active` | 疾病启用时允许；必须填写原因并写一条审计记录 |
| `active` | `active` | 幂等成功；不写重复审计 |
| `archived` | `archived` | 幂等成功；不写重复审计 |

`archived` 不是不可恢复终态，但在恢复前是完整只读状态。本次不引入更多状态，也不设计审批流、软删除状态或多阶段
生命周期。

### 3.3 归档只读边界

归档病例允许：

- 列出和查看病例；
- 查看病例全部访视；
- 查看和下载历史报告；
- 调用专用状态接口恢复为 `active`，前提是疾病仍启用。

归档病例禁止：

- 修改病例资料；
- 新增、整体替换、修改或删除访视；
- 物理删除病例；
- 启动新的纵向报告。

如需删除归档病例，必须先填写原因恢复为 `active`，再使用现有删除接口。

### 3.4 疾病停用与病例状态

疾病停用和病例归档是两套独立状态，不互相自动改写：

- 疾病停用后，现有病例和历史报告仍可查看；
- 疾病停用后，`active` 病例仍可归档，以便整理存量病例；
- 疾病停用后，`archived` 病例不能恢复为 `active`；
- 疾病停用后，无论病例状态如何，均禁止修改资料、维护访视、删除病例和启动新报告；
- 疾病重新启用且程序能力仍存在后，归档病例可以恢复。

### 3.5 权限

- `ai_operator` 可以归档和恢复自己拥有的病例；
- `admin` 通过现有操作者权限也可以归档和恢复自己拥有的病例；
- 管理员不会获得跨操作者病例访问能力；
- 病例不存在和病例属于其他用户继续统一返回 404，避免资源枚举；
- 本次不新增管理员审计查询 API 或审计页面。

### 3.6 报告、快照、数据集与模型

- 病例状态不写入报告输入快照；
- 病例状态不进入训练数据、模型特征、模型路由或预测结果；
- 归档不会改写既有报告、快照或 PDF；
- 已经成功创建并开始生成的报告继续按创建时快照完成；
- 归档只阻止归档后新发起的报告。

## 4. 方案比较与选择

### 4.1 数据库 CHECK 约束

优点：

- 与现有 `VARCHAR(50)` 兼容，迁移范围小；
- 直接 SQL 和并发写入最终都会被合法值约束拦截；
- 增加新值、回滚约束和全新建库同步较直接；
- 不把中文显示名称固化进数据库类型。

缺点：

- 只能约束合法值，不能表达转换原因、操作者和完整状态机；
- 状态集合需要在数据库、后端和前端映射中同步维护。

### 4.2 PostgreSQL ENUM

优点是数据库类型语义明确，非法值天然无法写入。缺点是删除或重命名枚举值、生产 downgrade 和多版本兼容成本较高；
当前状态规则刚被正式定义，使用 ENUM 会把业务演进和数据库类型演进绑定得过紧，因此不采用。

### 4.3 专用状态字典或关联表

适合状态由管理员动态维护、频繁扩展或包含大量展示元数据的系统。当前状态是两个稳定的系统内部代码，项目近期仍只运行
AD 和脂肪肝，引入字典维护、种子数据和关联查询属于过度设计，因此不采用。

### 4.4 仅后端 StrEnum、Pydantic 枚举或白名单

可以阻止正常 API 的非法输入，但内部 ORM、直接 SQL、临时脚本和并发旁路仍能写入未知状态，不能解决本次数据库级问题，
因此不能单独采用。

### 4.5 最终方案

采用以下组合：

```text
数据库合法值 CHECK
+ 后端统一 StrEnum/Pydantic 枚举
+ 集中状态转换服务
+ 所有病例写路径的行锁与 active 检查
+ 专用状态审计表
```

数据库负责“值一定合法”，应用层负责“谁可以在什么条件下从哪个合法值变到哪个合法值”。本次只实现两状态可逆转换，
不引入完整通用状态机框架。

## 5. 数据库设计

### 5.1 `operator_cases.status`

字段继续保持：

```sql
status VARCHAR(50) NOT NULL DEFAULT 'active'
```

新增约束：

```sql
CONSTRAINT ck_operator_cases_status
CHECK (status IN ('active', 'archived'))
```

ORM `__table_args__`、Alembic 和 `database/schema.sql` 使用相同约束名和相同英文 key。字段长度、非空要求和默认值不变，
不执行类型转换，也不改写既有病例。

### 5.2 专用状态审计表

新增 `operator_case_status_logs`：

| 字段 | 约束 | 作用 |
| --- | --- | --- |
| `id` | 主键 | 审计记录 ID |
| `case_id` | 可空外键，删除病例时 `SET NULL` | 病例仍存在时的关联 |
| `case_id_snapshot` | 非空整数 | 病例删除后仍保留原病例 ID |
| `actor_id` | 可空外键，删除账号时 `SET NULL` | 操作者仍存在时的关联 |
| `actor_id_snapshot` | 非空整数 | 账号删除后仍保留原操作者 ID |
| `from_status` | 非空字符串，合法值 CHECK | 变更前状态 |
| `to_status` | 非空字符串，合法值 CHECK | 变更后状态 |
| `reason` | 非空文本，去除首尾空格后 1～500 字符 | 人工填写的归档或恢复原因 |
| `created_at` | 非空时区时间，数据库默认当前时间 | 变更时间 |

附加约束：

- `from_status <> to_status`，审计表只记录实际变化；
- `from_status` 和 `to_status` 均只允许 `active|archived`；
- 原因不得为空白且不得超过 500 字符；
- 不复制患者标签、病例备注、访视或其他敏感医疗内容。

索引至少覆盖：

- `(case_id_snapshot, created_at)`；
- `(actor_id_snapshot, created_at)`。

状态服务在同一事务内更新病例并插入审计。病例或用户删除时，只清空可空外键，不删除审计记录。

### 5.3 数据库直接写入边界

- CHECK 会阻止直接数据库写入未知字符串；
- 数据库不会使用触发器自动生成状态审计，因为直接 SQL 缺少可信的业务操作者和原因；
- 合法状态之间的直接 SQL 修改可以绕过应用审计，因此生产应用账号和普通运维流程不得直接更新病例状态；
- 必须直接修复时，应走单独批准的数据变更方案，并显式补充审计，不属于日常 API。

## 6. 后端设计

### 6.1 单一状态定义

新增基于 `StrEnum` 的 `OperatorCaseStatus`，只定义 `ACTIVE = "active"` 与 `ARCHIVED = "archived"`。

- Pydantic 请求、响应和查询参数使用该枚举；
- 服务层比较枚举或其稳定字符串值；
- ORM 列继续使用 String 和 CHECK，不使用 SQLAlchemy PostgreSQL ENUM；
- 前端从 OpenAPI 语义和本地联合类型使用相同英文 key。

### 6.2 普通病例更新

- 从 `OperatorCaseUpdate` 中彻底删除 `status`；
- 保留 `extra="forbid"`；
- 旧客户端继续向普通更新接口提交 `status` 时返回 422，不静默忽略、不兼容转发；
- 普通更新接口只维护患者标签、年龄、性别、基线阶段和备注等资料。

### 6.3 专用状态接口

新增：

```http
PUT /api/v1/operator/longitudinal-cases/{case_id}/status
```

请求：

```json
{
  "expected_status": "active",
  "status": "archived",
  "reason": "本阶段随访结束"
}
```

字段规则：

- `expected_status` 必填且必须是合法枚举；
- `status` 为必填目标状态且必须是合法枚举；
- `reason` 去除首尾空格；实际发生状态变化时必须为 1～500 字符；
- 幂等请求不会生成审计，因此允许不提供原因；若提供仍须满足长度和非空白规则。

接口返回更新后的完整 `OperatorCaseOut`。

### 6.4 集中状态转换服务

状态接口只能调用集中服务。服务按以下顺序执行：

1. 按 `case_id + user_id` 查询病例并对病例行执行 `SELECT ... FOR UPDATE`；
2. 不存在或不属于当前用户时返回 404；
3. 如果数据库当前状态已经等于目标状态，按幂等成功返回，不重复审计；
4. 如果数据库当前状态不等于 `expected_status`，返回 409，要求客户端刷新；
5. 根据转换矩阵和疾病启用状态检查是否允许转换；
6. 实际变化时验证原因；
7. 更新病例状态并插入一条专用审计记录；
8. 在同一事务中提交并返回刷新后的病例。

如果更新或审计任一步失败，事务整体回滚，不能出现“状态已变但没有审计”或“有审计但状态未变”。

### 6.5 所有病例写路径的串行化

仅给状态接口加锁仍不足以形成生产级只读边界。以下操作都必须先锁定同一个 `operator_cases` 行，并在同一事务内确认
病例仍为 `active`：

- 修改病例资料；
- 删除病例；
- 新增访视；
- 整体替换访视；
- 修改访视；
- 删除访视；
- 创建新报告记录和输入快照。

所有写路径复用一个“锁定自有病例并检查写资格”的服务入口，避免每个接口自行维护状态判断。病例行锁作为病例级串行化点，
保证归档和其他写操作不会在检查之后互相穿透。

状态转换是例外入口：

- `active -> archived` 在疾病停用时仍允许；
- `archived -> active` 必须同时满足疾病启用和程序能力可用；
- 状态转换不能调用只允许 active 病例的普通写入口。

### 6.6 报告启动边界

报告路由在创建 `AIReport(status="generating")` 之前锁定病例行，重新确认：

- 病例属于当前用户；
- 病例状态为 `active`；
- 疾病启用且能力存在；
- 其他既有报告前置条件成立。

输入快照和报告记录在该受保护事务中创建并提交。提交后释放病例锁，流式模型生成不继续持锁。之后发生归档时，已经创建的
报告继续完成；新的报告请求会被归档状态拒绝。

### 6.7 列表筛选

现有列表接口增加可选状态参数：

```http
GET /operator/longitudinal-cases?status=active
GET /operator/longitudinal-cases?status=archived
GET /operator/longitudinal-cases?disease_id=1&status=archived
```

- 不传 `status` 时返回当前用户全部病例；
- 非法状态由 Pydantic 返回 422；
- 疾病筛选与状态筛选可以组合；
- 排序继续使用更新时间倒序和 ID 倒序。

## 7. API 错误语义

| 情况 | HTTP 状态 | 语义 |
| --- | --- | --- |
| 病例不存在或属于其他用户 | 404 | 病例不存在，不泄露所有权 |
| 非法状态 key、普通更新携带 status、字段格式错误 | 422 | 请求契约不合法 |
| 实际状态变化但原因缺失、空白或超长 | 422 | 状态变化原因不合法 |
| 当前状态与 `expected_status` 不一致，且不等于目标状态 | 409 | 状态已被其他操作修改，请刷新 |
| archived 病例执行资料、访视、删除或报告写操作 | 409 | 病例已归档，请先恢复 |
| 疾病停用时尝试恢复病例 | 409 | 疾病已停用，不能恢复病例 |
| 疾病停用时执行其他既有禁止写操作 | 409 | 疾病已停用，病例当前只读 |
| 数据库合法值或审计完整性约束意外失败 | 受控 409/500 并回滚 | 不泄露 SQL 和约束内部细节 |

错误响应使用稳定、易理解的中文说明。数据库 `IntegrityError` 只作为竞态和旁路写入的最后防线，正常业务错误应在服务层
提前识别。

## 8. 前端设计

前端修改遵循 `docs/DESIGN_SPEC.md` 的既有颜色、间距、圆角、按钮和无障碍规范。

### 8.1 状态显示与筛选

- 病例选择列表显示患者标签和状态标签；
- `active` 显示“使用中”，`archived` 显示“已归档”；
- 增加“全部 / 使用中 / 已归档”筛选，默认“全部”；
- 筛选调用后端 `status` 查询参数，不在客户端假装过滤已加载子集；
- 未知状态不回退成“使用中”，应显示受控的“未知状态”并记录前端异常，避免掩盖数据库问题。

### 8.2 状态操作

- 使用中病例显示“归档”入口；
- 已归档病例显示“恢复”入口；
- 操作弹窗必须说明结果并要求填写原因；
- 请求携带界面当前看到的 `expected_status`；
- 409 并发冲突时提示“病例状态已变化，请刷新后重试”，并重新加载病例；
- 不提供可自由输入状态的文本框或普通状态下拉框。

### 8.3 只读体验

归档病例：

- 病例资料和访视内容保持可见；
- 输入控件、保存、访视新增/删除和报告生成均禁用；
- 删除入口禁用或隐藏，并提示“请先恢复病例”；
- 页面显示明确的归档只读说明；
- 恢复成功并重新读取病例后，写操作恢复。

疾病停用与病例归档提示分别展示，不能让用户误以为恢复病例可以绕过疾病停用。疾病停用且病例为 active 时仍提供归档入口；
疾病停用且病例已归档时禁用恢复入口并说明原因。

## 9. 专用只读迁移前检查器

新增只读脚本，例如：

```text
scripts/check_operator_case_status_migration_readonly.py
```

脚本必须：

- 使用 `SET TRANSACTION READ ONLY`；
- 不执行 DDL、UPDATE、DELETE、INSERT 或自动修复；
- 不输出患者标签、备注或访视内容；
- 输出机器可读 JSON；
- 数据库不可达时返回 `BLOCKED`，不得伪装为通过。

至少检查：

- 当前 Alembic revision 与代码预期；
- `operator_cases.status` 的类型、长度、默认值和非空属性；
- `SELECT status, count(*) ... GROUP BY status` 的完整结果；
- NULL 数量；
- 不属于 `active|archived` 的未知值及其数量；
- 病例总数和合法状态数量合计是否一致；
- 目标约束和审计表当前是否已存在，以区分迁移前和迁移后状态；
- 迁移后约束是否 `convalidated = true`；
- 审计表字段、外键、删除规则、CHECK 和索引是否符合规格。

建议输出字段：

```json
{
  "status": "PASS",
  "mode": "empty_initialize",
  "operator_case_count": 0,
  "status_counts": [],
  "null_status_count": 0,
  "unknown_status_counts": [],
  "constraint_present": false,
  "constraint_validated": false,
  "audit_table_present": false
}
```

存在病例时 `mode` 为 `existing_validate`。任何 NULL、未知状态、字段契约偏差或迁移后未验证约束都返回 `FAIL`。未知值
只报告值和数量，不自动映射为预期状态。

## 10. 保守 Alembic 迁移策略

### 10.1 总原则

- 生产迁移前先备份并运行专用只读检查器；
- 不假设既有数据只有预期状态；
- 发现 NULL 或未知值立即停止，等待人工确认；
- 不自动将未知值改成 `active` 或 `archived`；
- 不删除病例、不重写历史报告、不修改报告快照；
- 迁移内部再次检查数据，不能只信任部署前检查结果。

### 10.2 空库

如果 `operator_cases` 为空：

- 保留现有非空字段和 `active` 默认值；
- 创建审计表；
- 增加状态 CHECK；
- 验证约束；
- `database/schema.sql` 对全新安装直接创建已验证 CHECK 和审计表。

空库不需要插入病例或状态种子数据。

### 10.3 既有库

建议使用两个连续 Alembic revision，并在生产中分两次命令执行，以保证约束增加和全表验证处于独立事务：

第一阶段 revision：

1. 检查 `status` 仍为 `VARCHAR(50) NOT NULL DEFAULT 'active'`；不符合则停止；
2. 短暂锁定 `operator_cases`，再次统计 NULL 和未知状态；
3. 发现异常立即抛错并整体回滚；
4. 创建 `operator_case_status_logs`、约束和索引；
5. 为病例状态增加 `ck_operator_cases_status CHECK (...) NOT VALID`；
6. 提交后，新写入立即受到 CHECK 保护。

第二阶段 revision：

1. 设置有限的 `lock_timeout` 和合理的 `statement_timeout`；
2. 执行 `VALIDATE CONSTRAINT ck_operator_cases_status`；
3. 验证 PostgreSQL 目录中 `convalidated = true`；
4. 失败时不部署应用写流量，排查后重新执行，不自动清洗数据。

`ADD ... NOT VALID` 仍需要短暂表级元数据锁；抢不到锁时应快速失败。`VALIDATE CONSTRAINT` 会扫描既有病例，但不会采用
重写整列的方式，普通读写风险低于直接改列类型。正式执行选择低流量时段，并在切换期间暂停纵向病例写请求，以消除
旧后端状态入口与新审计规则之间的窗口。

### 10.4 字段默认值、非空与增加顺序

当前字段已经非空且默认 `active`，迁移不先删除再重建默认值，也不临时放宽为可空。顺序固定为：

```text
只读预检
→ 迁移内复检
→ 创建审计结构
→ 增加 NOT VALID CHECK
→ 独立事务验证 CHECK
→ 部署新后端和前端
→ 迁移后只读核验
```

### 10.5 Downgrade

- 验证 revision 的 downgrade 可以将已验证 CHECK 重建为语义相同的 `NOT VALID` CHECK，不改写病例数据；
- 结构 revision 的 downgrade 可以删除病例状态 CHECK；
- 如果专用审计表为空，可以删除该空表和索引；
- 如果专用审计表已有任何记录，downgrade 必须停止并要求人工选择前向修复或先导出、保全审计数据，不能静默删除历史
  审计；
- downgrade 不删除病例、不修改病例状态、不删除报告，也不改写历史业务数据。

生产环境一旦已经产生状态审计，数据库结构回退不应作为常规应用回滚手段，应优先前向修复。

## 11. 旧数据与旧客户端兼容

### 11.1 旧数据

- 既有 `active` 和 `archived` 病例不改写；
- 既有报告和快照保持原样；
- 历史状态变化在本功能上线前没有可靠来源，不补造审计记录；
- 发现未知状态时停止迁移，由人工结合真实业务含义决定后续单独数据方案；
- 不以字符串相似、中文含义或出现频率自动猜测映射。

### 11.2 旧客户端

本次采用明确破坏性契约升级：

- 普通病例更新接口不再接受 `status`；
- 旧客户端提交 `status` 返回 422；
- 不提供兼容入口、不静默转发、不使用固定原因代替人工原因；
- 新前端与新后端必须协调发布；
- OpenAPI 和前端类型只公开专用状态接口。

## 12. 测试范围

### 12.1 数据库与迁移

- ORM 包含 `ck_operator_cases_status`，合法值与规格一致；
- `database/schema.sql` 包含同名已验证 CHECK 和完整审计表；

### 12.2 Pydantic、服务与 API

- 创建病例固定为 `active`；

- 状态变更、病例更新、访视写入和报告启动的并发测试验证病例行锁语义；

## 14. 生产部署、验证与回滚边界

### 14.1 部署前

- 确认仓库回归全部通过；
- 备份数据库并验证恢复路径；
- 运行专用只读检查器并人工审核 distinct status 和数量；
- 发现未知值、NULL、schema 偏差或 Alembic revision 不符时停止；
- 协调新后端和新前端同时发布，不允许旧客户端继续修改状态；
- 在数据库迁移与新后端切换期间暂停纵向病例写流量。

### 14.2 部署顺序

```text
暂停纵向病例写流量
→ 只读预检与人工确认
→ 执行第一阶段 Alembic revision
→ 单独执行验证 revision
→ 部署新后端
→ 部署新前端
→ 运行迁移后只读核验
→ 执行 active/archived、疾病停用和并发烟测
→ 恢复写流量
```

### 14.3 生产验证

- CHECK 存在且 `convalidated = true`；
- distinct status 只有 `active|archived`，总数与迁移前一致；
- 非法状态测试事务被数据库拒绝并回滚；
- 归档、恢复、幂等请求、并发冲突和审计记录正确；
- archived 病例所有写入口均被拒绝，读取和历史报告正常；
- 疾病停用时归档可用、恢复被拒绝；
- AD 和脂肪肝各完成一次受控烟测；
- 生产验证不使用真实患者敏感内容作为日志输出。

### 14.4 回滚边界

- 前端可单独前向修复或回滚，但后端状态保护必须保持；
- 一旦新状态服务已经产生审计记录，不得简单回滚到允许普通 PUT 修改 status 的旧后端；旧后端会绕过审计和归档只读规则；
- 新后端故障时优先暂停纵向病例写流量并前向修复；
- 只有尚未产生审计记录且经过人工确认时，才允许执行结构 downgrade；
- 任何回滚都不得删除病例、改写状态、删除历史报告或静默丢弃审计记录；
- 仓库代码部署完成不等于生产数据库迁移完成，两者必须分别记录。
