# P0-03 无未来泄漏固定窗口训练数据集设计

> 日期：2026-08-26
>
> 状态：待项目所有者书面审核
>
> 路线图任务：P0-03
>
> 适用疾病：脂肪肝、阿尔茨海默病（AD）

## 1. 设计结论

P0-03 将重建一条独立、只读、可审计的训练数据制作链路。重建范围仅限“怎样从现有纵向访视生成训练样本”，不推翻整个项目，也不替换当前线上预测服务。

每条候选样本站在一次历史访视日 `as_of`，只使用该日及以前的全部有效历史，判断下一阶段是否在未来 365 天内发生。模型可训练行仅包含标签明确的真实患者样本；观察不足、已经到达目标终点和合成数据仍进入审计，但不会混入正式训练数据。

本设计是当前项目和当前数据条件下的正式 P0-03 方案，不是先做一个临时最小版本。以后增加 AD 的正常到 MCI、CDR 1 到 2 等预测目标，属于新增数据集版本和新增模型目标，不是推翻本方案重做。

通俗地说：新建一条干净的“训练数据生产线”。它在患者过去每次复查时拍一张快照，只拿当时已经知道的资料预测下一年，绝不把患者后来的结果提前交给模型。

## 2. 背景与已核查基线

### 2.1 已发布基线

P0-03 以已经完成的 P0-01 和 P0-02 为输入基线：

- 数据库 revision/head 为 `0012`；
- 脂肪肝 current approved `version_id=3`，11 条正式规则，其中 10 条 calculable、1 条 evidence-only；
- AD current approved `version_id=4`，8 条 evidence-only 规则；AD calculable 和 projection 均为 0 是已确认的合法状态；
- 两种疾病的解析候选共 135 条，仍全部 pending、0 materialized；
- P0-02 的正式标准内容、版本和生命周期不在 P0-03 中修改。

### 2.2 旧 readiness 统计

现有 `longitudinal_readiness.v1` 的只读实测结果为：

| 疾病 | 患者 | 访视 | 旧历史前缀 | 旧阳性 | 旧阴性 | 旧未知 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 脂肪肝 | 300 | 1354 | 1054 | 146 | 908 | 0 |
| AD | 300 | 1365 | 1065 | 155 | 910 | 0 |

旧前缀从第 2 次访视开始生成，因此数量等于“总访视数减患者数”：

- 脂肪肝：`1354 - 300 = 1054`；
- AD：`1365 - 300 = 1065`。

这些是 P0-01 的旧 readiness 统计，不是 P0-03 的正式训练集统计。P0-03 改为至少 3 次访视，并采用更严格的标签证据，因此不能继续把 1054/1065 和 146/908、155/910 当作训练数据数量。

### 2.3 现有代码的关键问题

只读核查确认：

- 现有 `build_prefixes` 从第 2 次访视开始生成前缀；
- 现有 `outcome_label` 只判断最早事件是否满足 `as_of < event <= as_of+365`；
- 事件在 `as_of` 当日或以前时，旧逻辑可能将该前缀判为阴性，而不是先确定当前阶段；
- 即使未来观察不足 365 天，稳定最终阶段也可能使旧逻辑给出阴性；
- 现有训练脚本使用完整患者轨迹和最终 `confirmed` 等结果信息；
- 未知标签会被训练辅助逻辑直接过滤，缺少完整审计；
- 旧患者分组只使用 patient label，无法隔离不同 `source_dataset` 下的同名患者；
- `stage_label` 可能回退使用最终阶段；
- `final_stage`、`event_dates`、`confirmed`、完整轨迹 `total_visits` 和 `cohort_group` 等存在未来泄漏风险。

因此，P0-03 不继续修补旧 `outcome_label` 和旧训练脚本的数据制作路径，而是建立新的固定窗口构建器。

### 2.4 当前数据质量观察

当前两套参考数据的只读检查结果为：

- 未发现非法日期；
- 未发现同一来源、同一患者、同一天多条访视；
- 未发现排序后仍无法恢复的访视顺序问题；
- 已记录的事件日期均能对应某次访视；
- metadata 没有独立的 `last_followup_date`，可在审计时由患者最大有效访视日期重建；
- 患者级 `final_stage`、`event_dates` 和 `is_synthetic` 在该患者各次访视中一致。

这些观察仅描述当前数据，不会放松构建器的校验规则。

## 3. 目标与非目标

### 3.1 目标

P0-03 必须为两种疾病分别生成：

- 固定 365 天窗口的候选前缀；
- 不包含未来信息的模型特征；
- 明确的阳性、阴性、观察不足和不适用语义；
- 可供 P0-04 按患者划分数据的稳定 group ID；
- 包含来源、`as_of`、标签理由和证据的内部审计记录；
- 真实与合成数据完全分离的输出；
- 默认只读、无患者明细的稳定 JSON 摘要；
- 可重复生成且可通过内容摘要验证的数据文件。

### 3.2 非目标

P0-03 不负责：

- 训练、选择、调参、校准或评估 P0-04 模型；
- 生成 joblib、模型 metadata、registry 记录或任何生产模型 artifact；
- 修改纵向预测响应 schema；
- 修改 P0-02 的正式标准、规则、projection 或生命周期；
- 修改 P0-01 已发布的 `longitudinal_readiness.v1` 响应结构；
- 修改报告模板或前端 UI；
- 将训练集写入正式业务数据库；
- 删除现有合成数据；
- 在本任务中实现 AD 的正常到 MCI、CDR 1 到 2 或 CDR 2 到 3 预测。

完整 AD 阶段转换的当前边界和后续方向见：

`docs/superpowers/notes/2026-08-26-ad-stage-transition-future-design-note.md`

## 4. 方案比较与选择

### 4.1 方案 A：继续修补旧训练脚本

做法：修改现有 `outcome_label`、`build_prefixes` 和训练辅助函数，使其逐步满足 P0-03。

优点：新增文件较少。

缺点：旧代码把数据构建、完整轨迹处理和训练职责混在一起，容易保留 `confirmed`、最终阶段和旧标签语义；很难证明训练前没有泄漏。

结论：不采用。

### 4.2 方案 B：重写整个纵向预测系统

做法：同时重做数据导入、数据库结构、readiness、训练、registry、预测服务和报告链路。

优点：理论上可以一次统一全部接口。

缺点：超出 P0-03，风险和验证范围过大，会破坏已经发布的 P0-01、P0-02 及当前功能。

结论：不采用。

### 4.3 方案 C：重建独立的 P0-03 数据制作链路

做法：新建独立 dataset builder、schema 和 CLI；重新实现固定窗口标签；仅复用可靠的日期处理、疾病 adapter 和历史指标统计能力。

优点：可以从边界上隔离未来数据，标签和审计可独立测试，也不需要破坏现有预测功能。

缺点：旧 readiness 与新 P0-03 统计会暂时并存，文档和 CLI 必须明确二者含义不同。

结论：采用。这里的“重建”只针对训练数据制作部分，不是重做整个项目。

## 5. 总体架构

数据流固定为：

```text
只读加载数据库
→ 严格校验患者与访视
→ 按日期排序
→ 从第 3 次访视开始生成 as_of 候选
→ 仅用截至 as_of 的明确事件判断当前阶段
→ 确定下一阶段目标
→ 判断未来 365 天标签状态
→ 仅从截至 as_of 的历史提取特征
→ 执行特征允许列表和禁止字段检查
→ 分离真实与合成数据
→ 输出训练行、完整审计记录和匿名摘要
```

计划中的职责边界如下，最终文件名可在实施计划中按项目现有命名风格确认，但职责不得合并回训练脚本：

1. **只读加载层**：读取 `case_records` 及 metadata，不写数据库。
2. **数据校验层**：检查必需身份字段、日期、同日重复和患者级 metadata 一致性。
3. **疾病语义层**：复用 `disease_progression` adapter 的疾病名称、阶段顺序和正式事件字段映射，不复用旧 `outcome_label`。
4. **固定窗口标签层**：按本设计重新实现当前阶段、下一目标和 365 天标签。
5. **前缀特征层**：复用或小幅扩展 `longitudinal_features`，输入只能是已经截断到 `as_of` 的访视集合。
6. **泄漏防护层**：以明确特征允许列表为第一道边界，以递归禁止字段扫描为第二道边界。
7. **数据集组装层**：把身份审计、模型特征和标签证据放入彼此隔离的区域。
8. **CLI 与导出层**：默认只输出匿名 JSON 摘要；明确指定本地输出目录时才生成数据文件。

现有 `scripts/train_longitudinal_models.py` 和 `scripts/train_progression_model.py` 不再作为 P0-03 的数据来源。为了不破坏当前系统，本任务不删除旧脚本和旧模型；P0-04 的计划必须明确只读取新的 P0-03 正式训练文件。

## 6. 样本与字段分区

### 6.1 候选样本含义

一条候选样本表示：

> 站在某名患者一次真实访视的 `as_of` 当天，使用从首次有效访视到 `as_of` 的全部有效历史，判断该患者是否会在之后 365 天内进入本任务定义的下一阶段。

每条记录必须分为三个逻辑区域，防止后续训练器误读审计字段。

### 6.2 身份与审计区

仅用于追踪、分组和解释，不允许进入模型特征：

- schema/dataset version；
- disease；
- `source_dataset`；
- `patient_label`；
- `group_id`；
- `is_synthetic`；
- `source_document`、`import_version`（存在时）；
- `as_of`；
- 当前阶段；
- 本样本的下一阶段目标；
- 截至 `as_of` 的历史访视数；
- 历史起止日期；
- 数据质量和排序审计标记。

`patient_label` 是内部审计标识。`group_id` 是稳定的伪名化分组值，不应被描述为不可逆匿名标识。

### 6.3 模型特征区

只保存截至 `as_of` 已经可知的内容。模型训练器以后只能读取这一逻辑区域。

允许的特征类别：

- 当时可知的年龄和性别；
- 截至 `as_of` 的历史访视次数；
- 从首次访视到 `as_of` 的历史观察跨度；
- 距上一次访视的时间；
- 每项获准医学指标的首次值、最近值、最小值、最大值和均值；
- 首次到当前的变化量；
- 按真实访视日期计算的变化斜率；
- 最近两次有效测量之间的变化；
- 历史上升、下降次数；
- 实际测量次数和前缀内缺失比例。

AD 的历史 CDR 只有在该次 CDR 的访视日期不晚于 `as_of` 时才可作为历史特征。未来 CDR 和最终 CDR 绝不允许进入同期特征。

医学指标允许缺少一个或多个值。构建器保留已有值和缺失情况，不调用大模型、不做标签式推断，也不编造检查数值。

### 6.4 标签与证据区

用于筛选训练行和审计，不属于模型输入：

- `label_status`；
- 可训练二分类标签（仅明确时为 1 或 0）；
- 标签原因代码；
- 目标事件类型；
- 用于判定标签的事件日期；
- 窗口起止日期；
- 可用的最后随访日期；
- 未进入训练的具体原因。

审计记录可以保存事件日期作为判定证据，但导出器和未来训练器必须通过 schema 保证这些字段不可能进入模型特征。

## 7. 时间窗口和统一标签状态

### 7.1 时间边界

固定预测窗口为：

```text
(as_of, as_of + 365 天]
```

含义：

- `as_of` 当天发生的事件用于判断当前阶段，不算未来事件；
- `as_of` 次日起发生的目标事件可以计入阳性；
- 事件恰好发生在第 365 天，计为阳性；
- 第 365 天之后发生的明确目标事件，不是窗口内阳性。

### 7.2 标签状态

审计层使用四种互斥状态：

1. `positive`：窗口内明确发生目标事件，训练标签为 1；
2. `negative`：有充分证据确认窗口内未发生目标事件，训练标签为 0；
3. `insufficient_observation`：无法可靠确定窗口结果，不生成训练标签；
4. `not_applicable`：截至 `as_of` 已到达当前任务终点，没有可预测的下一阶段，不生成训练标签。

`insufficient_observation` 对应路线图中“未知标签必须统计”的语义，但对用户和审计输出采用更直白的“观察不足”，避免被误解为让大模型猜答案。它必须进入审计统计，绝不能默认为阴性。

### 7.3 阴性所需证据

只有满足以下任一条件，且不存在未定日期的进展证据时，才可标记为阴性：

- 患者的最大有效访视日期不早于 `as_of + 365 天`，且窗口内没有明确目标事件；
- 已有明确目标事件日期，并且该日期晚于 `as_of + 365 天`。

如果 `final_stage`、最终 CDR 或其他患者级结果显示目标进展最终发生过，但对应目标事件日期缺失，则不得利用随访长度把样本判为阴性，必须记为 `insufficient_observation`。

### 7.4 判定优先顺序

为避免同一记录被多种规则解释，顺序固定为：

1. 必需数据无效时整次构建失败；
2. 判断截至 `as_of` 是否已到达任务终点；
3. 若已到达，标记 `not_applicable`；
4. 查找窗口内明确目标事件，存在则标记 `positive`；
5. 检查是否存在“最终已进展但目标日期缺失”的冲突，存在则标记 `insufficient_observation`；
6. 检查是否满足阴性证据，满足则标记 `negative`；
7. 其余情况标记 `insufficient_observation`。

大模型不得参与上述任何标签判定。风险分数由 P0-04 使用明确标签训练模型后产生。

## 8. 疾病语义

### 8.1 脂肪肝

正式事件字段只使用：

- `cirrhosis_date`；
- `hcc_date`。

按 `as_of` 判断：

1. `hcc_date <= as_of`：当前已到达肝癌，状态为 `not_applicable`；
2. 否则，若 `cirrhosis_date <= as_of`：当前为肝硬化，下一目标为肝癌；
3. 否则：当前尚未进入肝硬化，下一目标为肝硬化；若明确记录为直接发生肝癌，则也视为发生下一阶段进展。

窗口内事件：

- 尚未肝硬化时，`cirrhosis_date` 或直接 `hcc_date` 落入窗口即为阳性；
- 已肝硬化时，仅 `hcc_date` 落入窗口为阳性。

`final_stage` 不能确定历史某天的阶段，也不能作为模型特征。若它显示最终已进展，但相应事件日期缺失，相关候选样本必须进入观察不足审计，不能伪装成阴性。

### 8.2 AD

AD 的业务阶段仍为：

```text
normal → mci → dementia
```

但 P0-03 当前唯一具有明确事件日期的正式目标是“进入痴呆”，事件字段只使用：

- `dementia_date`。

按 `as_of` 判断：

- `dementia_date <= as_of`：当前已经痴呆，状态为 `not_applicable`；
- `dementia_date` 落入未来窗口：`positive`；
- `dementia_date > as_of+365天`：可作为窗口阴性证据；
- 没有明确 `dementia_date`，但最终 CDR 或最终阶段明确显示已经进入痴呆：`insufficient_observation`；
- 其他情况按照统一随访证据判断阴性或观察不足。

不得自行发明 `mci_date` 或其他等价事件字段。MMSE、MoCA、CDR 和生化指标不得直接替代未来事件标签。历史访视中已经发生的 CDR 可以作为当时已知特征，但未来 CDR、最终 CDR 和完整轨迹汇总不得进入特征或反推过去阶段。

## 9. 前缀生成规则

### 9.1 最少访视数

- 患者必须至少拥有 3 次日期有效的访视，才会产生候选样本；
- 从第 3 次访视开始，每次访视都可以成为一个 `as_of`；
- 每个候选样本使用首次访视至 `as_of` 的全部有效历史，不是固定只取最近 3 次。

例如患者有 6 次访视，将产生 4 个候选前缀：

```text
第 3 次 as_of：使用第 1～3 次
第 4 次 as_of：使用第 1～4 次
第 5 次 as_of：使用第 1～5 次
第 6 次 as_of：使用第 1～6 次
```

因此，未来 AI 操作者输入至少 3 次访视与训练设计方向一致；模型仍可以利用 3～6 次乃至更多截至预测日的完整历史，不会被限制为只看 3 次。

### 9.2 日期排序和同日重复

访视唯一身份为：

```text
(source_dataset, patient_label, visit_date)
```

规则：

- 输入顺序混乱但日期合法时，构建器按日期升序排序，并在摘要中记录发生过重排；
- 同一来源、同一患者、同一自然日出现多条访视时，整次构建失败并报告冲突计数；
- 不自动合并、不选择其中一条，也不依赖原始行顺序打破平局；
- P0-03 暂不新增数据库唯一约束，避免超出只读数据集构建范围。

### 9.3 缺失和非法数据

以下构建必需字段缺失或无效时，整次构建失败：

- `source_dataset`；
- `patient_label`；
- `visit_date`。

这里不包括医学检查指标。某次访视缺少 ALT、AST、MMSE、CDR 或其他一个或多个医学指标时，允许继续构建；程序只记录该指标缺失，不删除整个患者，也不编造数值。

患者级 metadata 在同一患者各次访视间互相冲突时，整次构建失败，避免静默选择某个最终结果。

## 10. 稳定患者 group ID

患者身份由以下二元组确定：

```text
(source_dataset, patient_label)
```

`group_id` 使用版本固定的规范化和 SHA-256 生成：

1. 两个字段必须是非空字符串；
2. 去除首尾空白，并进行 Unicode NFC 规范化；
3. 以无歧义的 JSON 二元数组进行 UTF-8 编码；
4. 计算完整 SHA-256，并加固定版本前缀。

同一患者的所有候选前缀必须具有同一 `group_id`。不同 `source_dataset` 下即使 `patient_label` 相同，也必须得到不同 group ID。

`group_id` 只用于 P0-04 按患者划分训练集、验证集和测试集，绝不进入模型特征。

## 11. 真实与合成数据隔离

当前合成数据不删除，但必须与真实数据严格隔离：

- 构建和摘要分别统计真实与合成患者；
- 正式训练文件只包含真实患者的明确阳性和阴性样本；
- 合成候选样本只进入单独的内部审计文件；
- P0-04 的正式训练、验证和测试默认只读取真实训练文件；
- 合成数据不得影响正式风险分数、报告内容或相似病例结果；
- 面向 AI 操作者的使用流程不展示合成数据提示或合成病例；
- 如果未来希望合成数据影响正式结果，必须另行设计并获得明确授权。

`is_synthetic` 是审计和路由字段，不是模型特征。

## 12. 特征泄漏防护

### 12.1 第一层：只从历史前缀构造

特征函数只能接收已经截断为 `visit_date <= as_of` 的不可变访视集合。调用者不能把完整患者轨迹传给特征函数后再依赖函数内部忽略未来记录。

### 12.2 第二层：明确允许列表

特征 schema 只允许第 6.3 节定义的历史统计类型。身份、来源、标签、事件证据和患者最终结果没有进入特征 schema 的入口。

### 12.3 第三层：禁止字段扫描

在生成任何训练文件前，对模型特征键执行递归、大小写不敏感的禁止检查。至少禁止：

- `final_stage`；
- `confirmed`；
- `event_dates`；
- `cirrhosis_date`；
- `hcc_date`；
- `dementia_date`；
- `fatty_liver_date`；
- `last_followup_date`；
- `lost_to_followup`；
- 完整轨迹 `total_visits`；
- 原始 `visit_index`；
- `cohort_group`；
- `outcome_source`；
- `assigned_final_stage`；
- `inferred_stage`；
- 标签和标签理由；
- 数据生成路径、规则路径和其他可直接识别合成来源的字段；
- `source_dataset`、`patient_label`、`group_id`、`is_synthetic` 等身份或分组字段；
- 任意 `as_of` 之后访视的指标，包括未来 CDR。

禁止列表是第二道保险，不能替代允许列表和时间截断。如果发现禁止字段，整次构建失败，不输出看似正常的数据集。

### 12.4 审计字段与模型字段物理隔离

导出记录的 schema 必须把 `features` 放在独立对象中。未来训练器只能解析版本化的 `features` schema，禁止使用“删除几列后把剩余全部训练”的方式。

## 13. 输出与 CLI 行为

### 13.1 默认只读检查

P0-03 提供独立 CLI。默认运行时：

- 只读数据库；
- 不训练模型；
- 不写数据库；
- 不生成模型 artifact；
- 不输出患者编号、group ID 或逐条明细；
- 只向标准输出写入 UTF-8 稳定 JSON 摘要。

摘要至少按疾病和真实/合成来源分别统计：

- 患者数；
- 访视数；
- 候选前缀数；
- `positive`；
- `negative`；
- `insufficient_observation`；
- `not_applicable`；
- 可训练行数；
- 因质量问题导致的失败类型和计数；
- 发生日期重排的患者或访视计数。

构建失败时仍不得在终端输出患者隐私；具体冲突明细只能进入明确指定的受控本地审计输出，或在开发测试夹具中验证。

### 13.2 明确导出

只有调用者明确指定本地输出目录时，才允许写文件。按疾病分目录输出：

- `real_train.jsonl`：真实患者中标签明确的阳性和阴性训练行；
- `real_audit.jsonl`：真实患者的全部候选样本，包括观察不足和不适用；
- `synthetic_audit.jsonl`：合成患者的全部候选样本，独立保存；
- `manifest.json`：dataset/schema version、规则版本、窗口、来源统计、代码版本和文件内容摘要。

默认不覆盖已经存在的目标文件，避免误覆盖既有审计结果。输出采用 UTF-8、固定字段结构和固定排序。

### 13.3 确定性与内容摘要

排序键至少包含：

```text
disease, source_dataset, patient_label, as_of
```

同一数据库状态、同一代码版本和同一配置重复运行时：

- JSONL 训练行内容及顺序必须相同；
- 每个数据文件的 SHA-256 必须相同；
- manifest 中单独记录稳定的数据内容摘要；
- `generated_at` 等运行时字段不得参与稳定数据内容摘要，因此生成时间不同不会伪装成数据变化。

## 14. 与现有组件的关系

### 14.1 可以复用

- `disease_progression` 中可靠的疾病 adapter、阶段名称和正式事件字段定义；
- `longitudinal_features` 中只依赖已截断历史的基础指标统计；
- 现有数据库只读会话、日期解析和 UTF-8 JSON 输出模式；
- P0-01 已验证的敏感信息过滤方法；
- P0-02 已发布的疾病和 canonical indicator 基线，只读使用，不修改。

### 14.2 必须新增或替换

- 独立的固定窗口 dataset schema；
- 严格的三次访视前缀生成器；
- 当前阶段和下一阶段目标解析；
- 新的 365 天标签状态机；
- 完整观察证据与未定日期进展冲突检查；
- 稳定、跨来源隔离的 group ID；
- 特征允许列表与禁止字段扫描；
- 真实/合成隔离；
- 训练行与全量审计的双输出；
- 默认只读的 P0-03 JSON 审计 CLI；
- 确定性排序、manifest 和文件摘要。

### 14.3 暂不修改

- `longitudinal_readiness.v1` 的响应 schema；
- 当前线上预测服务和报告；
- 旧模型文件和 registry；
- P0-02 标准数据；
- frontend。

P0-01 readiness 与 P0-03 新审计在一段时间内会显示不同前缀和标签统计，这是预期行为：前者保留已发布契约，后者才是 P0-04 的训练数据依据。

## 15. 错误处理原则

### 15.1 整次构建失败

以下问题会使整次构建失败，不产生部分训练文件：

- 构建必需身份字段缺失；
- 日期缺失或非法；
- 同患者同日重复访视；
- 同一患者的关键 metadata 冲突；
- 特征中发现禁止字段；
- 输出 schema 校验失败；
- 写出过程中无法保证文件完整性。

### 15.2 记录为观察不足

以下不是数据格式错误，不使整次构建失败，但相关候选样本不进入训练：

- 未来观察不足 365 天，且没有明确窗口后事件日期；
- 已知最终发生目标进展，但缺少明确事件日期；
- 无法依据正式事件字段确定窗口结果。

### 15.3 记录为不适用

截至 `as_of` 已经达到当前预测任务终点时，只保留审计，不进入训练。例如：

- 脂肪肝患者截至 `as_of` 已发生肝癌；
- AD 患者截至 `as_of` 已发生痴呆。

## 16. 测试策略

实现必须采用 TDD：先写并运行失败测试，再写最少生产代码使测试通过。设计文档审核通过后，另行编写详细实施计划；计划获批前不得写生产代码。

至少覆盖以下测试：

### 16.1 时间截断和边界

- 第 4 次访视作为 `as_of` 时，特征只包含第 1～4 次；
- 第 5 次及之后的访视、指标和 CDR 不得影响该样本特征；
- 事件恰好发生在 `as_of` 当天时不算未来阳性；
- 事件发生在 `as_of+1天` 时算阳性；
- 事件恰好发生在 `as_of+365天` 时算阳性；
- 事件发生在第 366 天时不算窗口内阳性，并可作为阴性证据。

### 16.2 标签证据

- 完整覆盖 365 天且无事件时为阴性；
- 观察不足且无明确窗口后事件时为观察不足；
- 已知最终进展但缺少事件日期时为观察不足而非阴性；
- 过滤观察不足后，审计摘要仍保留其数量；
- 不适用样本不进入训练行。

### 16.3 疾病语义

- 脂肪肝尚未肝硬化时正确识别 `cirrhosis_date`；
- 脂肪肝直接发生 HCC 时正确识别进展；
- 已肝硬化时只预测 HCC；
- 已 HCC 时为不适用；
- AD 只使用 `dementia_date` 作为目标事件；
- AD 不以 MMSE、MoCA、未来 CDR 或生化指标代替标签；
- AD 最终 CDR 显示痴呆但缺少 `dementia_date` 时为观察不足。

### 16.4 前缀、缺失和身份

- 少于 3 次访视不生成候选前缀；
- 3～6 次访视分别生成预期数量的全部历史前缀；
- 医学指标缺失不会导致整个患者被拒绝；
- 必需身份或日期缺失时构建失败；
- 合法乱序会被排序并计入审计；
- 同日重复访视导致整次构建失败；
- 同一患者所有前缀具有相同 group ID；
- 不同来源下相同 patient label 不会被错误合并。

### 16.5 泄漏防护

- 禁止列表拦截 `final_stage`、`event_dates`、`confirmed`；
- 拦截疾病事件日期、最终随访、完整轨迹总访视数和原始 `visit_index`；
- 拦截最终/未来 CDR；
- 拦截身份、来源、合成标记和标签理由进入 `features`；
- 特征函数只能接收截断后的历史集合。

### 16.6 隔离、CLI 与可重复性

- 正式训练文件只有真实患者的阳性和阴性行；
- 合成候选只进入独立审计文件；
- CLI 默认不训练、不写数据库、不写数据文件；
- 默认 JSON 摘要不包含患者标识；
- 明确导出后文件结构、排序和摘要正确；
- 当前真实数据库的双疾病统计能够重复生成；
- 相同数据库、代码和配置重复导出的稳定内容摘要相同。

## 17. 当前数据规模预估

在设计核查阶段，按“真实患者、至少 3 次访视、365 天和严格标签”的临时只读计算得到：

| 疾病 | 有可训练前缀的真实患者 | 可训练前缀 | 阳性 | 阴性 |
| --- | ---: | ---: | ---: | ---: |
| 脂肪肝 | 106 | 200 | 59 | 141 |
| AD | 88 | 165 | 56 | 109 |

这些数字用于验证设计方向和判断 365 天窗口是否可行，不是手工写死的验收常量。正式数量必须由完成后的 P0-03 构建器从真实数据库只读重算，同时完整报告观察不足和不适用数量。

365 天相对 180 天和 730 天的只读比较结果为：365 天在两种疾病上的阳性数量较均衡；180 天会进一步减少 AD 阳性；730 天会明显增加未来观察不足。因此本设计固定采用 365 天。

## 18. 验收标准

P0-03 只有同时满足以下条件才算完成：

1. 两种疾病均能从当前数据库只读构建；
2. 每个候选样本至少包含 3 次截至 `as_of` 的有效访视；
3. 所有模型特征均可证明来自 `as_of` 当天或以前；
4. 阳性、阴性、观察不足和不适用状态互斥且有稳定原因代码；
5. 观察不足不进入训练行，但保留在审计记录和摘要；
6. 真实训练数据与合成数据完全隔离；
7. 同一患者不会跨训练/验证分组所需的 group 边界；
8. 禁止字段混入特征时构建失败；
9. 默认 CLI 不写数据库、不训练模型、不生成 artifact、不泄露患者明细；
10. 相同输入重复构建得到相同训练内容摘要；
11. 所有单元测试、集成测试和当前相关回归测试通过；
12. 不修改 P0-02 已发布标准，不修改 frontend 和线上预测 schema。

## 19. 后续衔接

P0-03 完成后，P0-04 才可以使用 `real_train.jsonl` 训练固定窗口风险模型。P0-04 必须：

- 只按 `group_id` 做患者级划分；
- 默认只使用真实患者；
- 只读取版本化 `features` 和明确的 0/1 标签；
- 不从审计字段重新拼接特征；
- 生成风险分数，而不是要求 P0-03 或大模型给观察不足样本补答案。

P0-04 的模型、超参数、校准、artifact 和 registry 设计不在本文展开。

## 20. 已确认决定摘要

- 采用独立重建 P0-03 数据制作链路；
- 窗口为 `(as_of, as_of+365天]`；
- 至少 3 次访视，从第 3 次开始生成，使用截至当日的全部历史；
- 脂肪肝按当前阶段预测肝硬化或肝癌下一进展；
- AD 当前正式目标只认 `dementia_date`；
- 阴性必须有完整随访或明确窗口后事件证据；
- 无法判断的样本称为“观察不足”，必须审计、不得默认为阴性；
- 同患者同日重复访视使整次构建失败；
- 医学指标局部缺失允许继续，身份和日期等必需字段缺失才失败；
- group ID 同时包含来源和患者编号语义，且不作为特征；
- 真实与合成数据严格隔离，正式模型默认只使用真实患者；
- 默认 CLI 只读、匿名汇总，不训练、不写数据库；
- P0-03 不修改 P0-02、前端、线上响应或现有模型 artifact。
