## 第 1 项：操作者建立病例

### 目标流程

操作者先建立一个匿名病例，选择疾病并填写病例基本资料；病例保存成功后，再进入后续的访视录入流程。

### 当前已经具备

- 电脑端有“新建纵向病例”和病例编辑页面。
- 疾病选择页面目前只显示“脂肪肝”和“阿尔茨海默病”。
- 后端提供病例新增、查询、修改和删除接口。
- 病例按操作者账号隔离，操作者不能通过接口查看其他操作者的病例。
- 数据库可以保存病例内部标签、疾病、年龄、性别、基线阶段、备注和状态。
- 病例接口受到 AI 操作者权限保护。
- 相关专项验证通过：后端病例服务和 schema 测试 `9 passed`，前端病例同步合约通过。

### 当前缺失或不符合目标流程的部分

1. 性别可以不填写，无法保证后续模型输入完整。
2. 后端只检查疾病 ID 是否存在，没有在病例接口层明确限制只能建立脂肪肝或 AD 病例。
3. “病例内部标签”是自由文本，没有强制使用匿名编号，存在误填患者姓名等身份信息的风险。
4. 当前前端允许先保存一个空病例再录入访视；但这仍未形成完全独立的流程，因为点击“保存病例”后会立即启动报告生成。
5. 点击“保存病例”后会立即启动报告生成，建立病例和生成报告被混成了一步。
6. 前端保存按钮的 loading 状态只覆盖事件派发，没有完整等待后端保存请求结束。
7. 目前已有接口和代码契约测试，但还缺少“页面提交 → 真实接口 → 数据库落库”的完整验收测试。

### 结论

第 1 项目前是“可以运行”，但还没有完全符合流程图中“先建立病例、再录入访视”的独立步骤。后续整理方向应为：

```text
建立匿名病例
→ 选择脂肪肝或 AD
→ 填写年龄、性别、基线阶段
→ 单独保存成功
→ 再进入访视录入
```

本项已由用户确认。下一项“录入多次访视”待用户确认后再开始核查和补充。

## 第 2 项：录入多次访视

### 目标流程

在病例建立成功后，操作者为同一病例按日期录入多次访视；每次访视包含指标名称、数值、单位和备注，形成可用于纵向分析的时间线。

### 当前已经具备

- 数据库有独立的 `operator_case_visits` 访视表。
- 每次访视可以保存访视日期、访视序号、指标名称、指标数值、单位和访视备注。
- 前端可以添加和删除访视，也可以在一次访视中添加多个指标。
- 同一病例不允许使用重复的访视日期。
- 每个病例最多保存 10 次访视。
- 无论操作者按什么顺序录入，系统都会按访视日期排序并重新编号。
- 可以整批替换一个病例的完整访视时间线，编辑多次访视时不会因为日期调整产生临时唯一键冲突。
- 访视数据会写入报告输入快照，历史报告可以保留当时实际使用的访视内容。
- 访视、特征和预测相关专项验证通过：后端 `50 passed`，前端病例同步合约测试通过。

### 当前缺失或不符合目标流程的部分

1. 没有最低访视次数限制。现在可以保存 0 次访视的病例，并尝试直接生成报告；这种病例无法形成有意义的纵向预测。
2. 前端保存按钮没有完整等待后端请求。编辑器只是派发保存事件，真正的保存由父页面异步完成，按钮可能在数据库请求结束前就停止 loading。
3. 整批保存会删除并重新创建访视记录，因此访视数据库 ID 可能改变。当前报告依靠不可变输入快照，所以历史报告正文不会被重新计算；但其他功能不能假设访视 ID 永久不变。
4. 访视字段仍然较简单，没有记录检测来源、检测设备或实验室、是否为基线访视、用药或治疗变化、诊断变化，以及 AD 量表版本/语言/教育校正或脂肪肝影像检查类型。
5. 指标名称和单位仍是自由文本。例如 `ALT`、`alt`、`谷丙转氨酶` 可能被当作不同指标，单位也没有在录入时统一。
6. 没有按疾病显示访视所需指标。脂肪肝和 AD 共用同一种通用“添加指标”方式，操作者无法从页面明确知道当前疾病必须录入哪些关键指标。

### 结论

第 2 项目前是“多次访视可以保存和排序”，基础功能已经存在，但还不够适合作为脂肪肝和 AD 的正式输入流程。后续正式流程应整理为：

```text
病例保存成功
→ 至少录入规定数量的有效访视
→ 每次访视填写日期
→ 选择该疾病允许的指标
→ 使用统一单位
→ 保存完整时间线
```

本项已由用户确认。下一项“校验指标、单位、年龄、性别和基线阶段”待用户确认后再开始核查和补充。

## 第 3 项：校验指标、单位、年龄、性别和基线阶段

### 目标流程

操作者提交病例和访视后，系统在调用模型前统一检查五类输入：年龄、性别、基线阶段、指标名称和指标单位。只有与当前疾病及模型契约兼容的输入才能进入推理；不完整或不兼容时，应明确说明原因并安全停止或降级。

### 1. 指标名称

当前已经具备：

- 指标名称会去除首尾空格。
- 同一次访视不能重复填写同名指标。
- 空指标名称会被拒绝。
- 特征生成时会将指标名称转为小写，例如 `ALT` 和 `alt` 会进入同一个计算键。
- 脂肪肝关键指标包括 ALT、AST、GGT、TBIL、ALB、PLT、AFP。
- AD 关键指标包括 MMSE、MoCA、CDR、血浆 NfL、血浆 p-tau217。

当前缺失：

- 操作者页面仍使用自由文本框输入指标名称，没有提供固定指标字典。
- “固定指标字典”是指：操作者从当前疾病已确认的指标清单中选择指标，页面显示中文名称和英文缩写，后端始终接收统一代码。例如页面显示“丙氨酸氨基转移酶（ALT）”，实际提交标准代码 `alt`。
- 没有把“谷丙转氨酶”等中文别名自动映射到 `alt`。
- 没有在保存前阻止录入与当前疾病无关的指标。

固定指标字典的目标交互为：

```text
选择疾病：脂肪肝
选择指标：丙氨酸氨基转移酶（ALT）
标准代码：alt（系统内部使用）
单位：U/L（自动带出）
数值：42
```

### 2. 单位

当前已经具备：

- 单位不能为空，并会去除首尾空格。
- 同一指标在不同访视中单位不一致时，系统会标记为 `conflict`。
- 单位缺失时会标记为 `missing`。
- 报告可以显示单位缺失或冲突状态。

当前缺失：

- 没有单位字典和单位别名标准化。
- 没有统一处理 `IU/L`、`U/L`、`u/l` 等表示方法。
- 没有单位换算。
- 单位冲突目前主要用于报告提示，不是在录入时阻止错误输入。
- 没有根据疾病和指标检查所填单位是否允许。

### 3. 年龄

年龄输入链路已完成首轮生产化补齐：

- 脂肪肝结局模型和阶段模型使用 `age`。
- AD 结局模型和阶段模型使用 `age`。
- 正式训练特征中存在年龄字段。
- Alembic `0013` 为 `operator_cases` 增加可空整数年龄列，并使用数据库检查约束限制为 `0–120`。
- 新建病例的后端 schema 和前端表单都要求填写 `0–120` 的整数年龄；更新时可省略年龄，但不能显式清空。
- 旧病例允许继续读取；年龄为空时，系统会在创建报告记录和加载模型前拒绝生成新报告，并提示先补录年龄。
- 年龄会保存到报告输入快照，并传入固定窗口和模型组两条纵向推理特征路径；年龄 `0` 不会被误判为缺失。
- 模型 metadata 仍保留对历史缺失值的兼容能力，但操作者的新报告链路不再允许缺失年龄进入推理。
- 本轮年龄专项整体验证通过：后端 `126 passed, 2 subtests passed`，前端年龄、病例同步、基线阶段和报告 UI 共 `12` 个契约子测试通过，生产构建完成。

### 4. 性别

当前已经具备：

- 后端只接受 `male` 或 `female`。
- 前端只能选择男或女。
- 性别会进入报告输入快照。
- 部分脂肪肝和 AD 模型会使用性别特征。
- 参考标准解析会按性别筛选适用规则。

当前缺失：

- 性别目前可以不填写。
- 模型 metadata 允许性别缺失。
- 生成报告前没有明确展示“性别缺失会影响哪些模型或参考标准”。

### 5. 基线阶段

基线阶段是五类输入中完成得相对最好的一项：

- 脂肪肝和 AD 使用不同的阶段选项。
- 切换疾病时，如果原阶段不属于新疾病，页面会自动清空。
- 后端支持中文阶段名称和英文阶段代码的标准化。
- 阶段缺失、未知、相互冲突或属于其他疾病时会安全降级，不会强行给出风险结果。
- 已肝癌、已痴呆等终末阶段会被识别为预测任务不适用。

### 当前总体状态

| 输入 | 当前状态 |
| --- | --- |
| 指标名称 | 有基础清洗；标准 manifest 已提供 `canonical_key` 和 `aliases`，可作为固定指标字典的数据源，但操作者页面尚未直接使用这套字典完成选择和校验 |
| 单位 | 能发现缺失或冲突，但没有统一、限制和换算 |
| 年龄 | 已建立 `0–120` 整数录入、数据库约束、快照和两条模型特征传递；旧病例生成新报告前必须补录 |
| 性别 | 可以传递，但不是必填，也没有完整性影响提示 |
| 基线阶段 | 有疾病专属选项、标准化和安全降级 |

专项验证结果：后端输入、特征、预测、阶段路由和标准解析测试 `73 passed`；前端基线阶段测试 `3 passed`。

### 结论

第 3 项目前只有基础格式校验，还没有形成真正的模型输入校验门。后续正式流程应为：

```text
选择疾病
→ 填写年龄和性别
→ 选择该疾病允许的基线阶段
→ 从该疾病固定指标字典（可由标准 manifest 的 `canonical_key` 和 `aliases` 生成）中选择指标
→ 自动带出或选择规定单位
→ 检查必需字段、别名和单位兼容性
→ 通过后才允许调用模型
```

本项已由用户确认。下一项“调用当前疾病模型”待用户确认后再开始核查和补充。

## 第 4 项：调用当前疾病模型

### 目标流程

```text
病例疾病
→ 转换为 fatty_liver 或 ad
→ 读取对应 active 指针
→ 加载对应 release set
→ 评审/启用时校验 review；加载时校验 artifact、metadata、路径和哈希
→ 根据基线阶段选择结局任务
→ 调用结局模型、阶段模型和趋势模型
→ 将结构化结果交给报告生成器
```

### 当前活动模型组

- 脂肪肝活动指针：`backend/app/ml_models/active/fatty_liver.json`。
- AD 活动指针：`backend/app/ml_models/active/ad.json`。
- 脂肪肝 release set：`fatty_liver-6f9c8a2da687-a13186ccaa8f`，共 10 个模型，其中 2 个结局模型、1 个阶段模型、7 个趋势模型。
- AD release set：`ad-6f9c8a2da687-3acb488b1a87`，共 7 个模型，其中 1 个结局模型、1 个阶段模型、5 个趋势模型。

脂肪肝会按基线阶段选择结局任务：

```text
未肝硬化 → fatty_liver.pre_cirrhosis_to_progression
肝硬化   → fatty_liver.cirrhosis_to_hcc
```

AD 的 `normal`、`mci` 和 `pre_dementia` 阶段使用：

```text
ad.pre_dementia_to_dementia
```

### 当前已经具备

- 两个病种使用独立的 active 指针和 release set，不会串用另一病种的模型。
- 评审或启用 release set 时会校验 review；实际加载时会校验 artifact、metadata、文件路径和哈希。
- 任务与模型不匹配时会拒绝调用。
- 模型或 metadata 缺失、损坏时会返回稳定的错误状态，而不是继续输出不明结果。
- 结局模型、阶段模型和趋势模型分开执行。
- 单个趋势模型失败时，其他趋势结果仍可保留。
- 阶段模型失败时不猜测阶段。
- 未校准模型会提示分数不代表临床概率。
- 报告会记录 release set ID 和数据版本，前端可以显示模型组版本及参与状态。
- 相关专项验证通过：模型注册、artifact、metadata 和 release set 测试 `21 passed`；推理任务选择、模型组一致性和失败隔离测试 `4 passed`。

### 当前缺失或不符合目标流程的部分

1. 当前活动模型来自合成演示数据。manifest 标记 `formal_training_source = synthetic_demonstration`、`synthetic_in_formal_metrics = true`、`clinical_validity_claim = false`，且模型 metadata 标记 `production_enabled = false`；因此目前只能说明工程链路可运行，不能说明模型具有临床有效性，也不应直接作为生产临床模型宣称。多个趋势模型目前还出现相同 artifact 哈希，需要在后续模型审计中确认是否为有意复用。
2. 完整 release set 的输入检查主要按 metadata 排列特征，除年龄外的其他严格必需字段还没有在调用前统一列出；缺失输入可能直到模型处理或推理失败时才暴露给操作者。
3. active 指针或 release set 加载失败时，API 可能已经先创建 `generating` 状态的报告；如果随后加载异常，报告可能停留在 `generating`，不能稳定落为失败状态。
4. 没有模型缓存，每次生成报告都会重新读取活动模型组和模型文件。

### 安全降级边界

- 基线阶段缺失：不估计对应结局。
- 跨疾病或未知阶段：禁用不兼容任务。
- 已肝癌或已痴呆等终末阶段：任务不适用。
- 结局模型缺失：不输出风险结果。
- 阶段模型失败：不猜测阶段。
- 单个趋势模型失败：保留其他成功趋势。
- 分数异常：标记为不兼容。
- 整体生成异常：返回安全错误消息，不泄露内部详情。

### 结论

第 4 项的模型注册、版本校验、任务路由和基础失败隔离已经存在，年龄输入链路也已补齐；但当前模型仍是合成演示模型，其他严格输入门和生成失败状态收敛仍需补齐。后续正式接入应保证：

```text
只调用与疾病和阶段匹配的活动模型组
→ 先完成完整输入契约校验
→ 记录模型组版本和输入快照
→ 任何加载或推理异常都明确落为失败或安全降级
```

本项已由用户确认。下一项“结合对应疾病标准和参考病例”待用户确认后再开始核查和补充。

## 第 5 项：结合对应疾病标准和参考病例

### 目标流程

模型完成结构化预测后，系统应根据当前疾病选择对应的正式标准和合适的参考病例，并在报告中明确区分：观察事实、标准解释、参考病例信息和模型预测。标准或参考病例不能被当作模型预测本身，也不能由 LLM 自行补充医学结论。

### 当前已经具备

- 脂肪肝和 AD 使用各自独立的标准版本，不会混用。
- 标准版本有审批状态、版本号、规则编号、适用条件和来源哈希。
- 脂肪肝当前标准包含 11 条正式规则，其中 10 条可计算、1 条仅供证据参考。
- AD 当前标准包含 8 条正式规则，全部为 `evidence-only`，没有可直接计算的 AD 数值阈值。
- 标准适用条件不满足时，会降级为“仅供证据参考”，不会强行计算。
- 标准冲突、标准缺失和适用条件缺失会记录为警告。
- 报告会保存标准来源、版本 ID、规则 ID 和适用性信息。
- 系统只选择同病种、已确认的参考病例，并按当前活动数据版本过滤。
- 参考病例会去重，并记录与当前病例重叠的指标。
- 合成参考病例会显示“来自合成或规则重组数据”的警告。
- 报告正文把观察事实、标准解释和模型预测分开。
- 相关专项验证通过：标准、证据选择和报告渲染测试 `57 passed`。

### 当前缺失或不符合目标流程的部分

1. AD 的 MMSE、MoCA、CDR、NfL、p-tau217 等当前规则全部是证据型规则。系统不能根据这些数值直接说“异常”“确诊”或“必然进展”。
2. 操作者调用标准时主要传入性别，没有完整传入 AD 量表版本、教育程度、评估语言、样本类型、检测平台、检测方法、年龄和基线阶段。因此即使标准存在，也可能只能以证据参考形式出现。
3. 参考病例目前主要按“同病种且有重叠指标”筛选，没有按年龄、性别、基线阶段、指标数值、变化方向、观察跨度、治疗或诊断变化和结局来源可靠性计算真正的相似度。
4. 参考病例来源会带出 `patient_label`。如果以后导入的数据标签包含真实姓名、住院号或其他身份信息，可能被写进报告；当前没有强制转换为匿名参考编号。
5. 合成病例的结局可能来自规则重组或人工分配。它们可以用于流程和算法回归，但不能作为真实病例证据或临床依据；当前报告虽有合成警告，但结局来源说明仍不够完整。
6. 标准查询或参考病例查询发生异常时，接口会清空来源后继续生成报告。操作者看到的可能只是“没有可用标准”，无法区分标准确实缺失和查询过程失败。
7. 报告保存了标准版本 ID、规则 ID 和哈希，但没有完整展示标准文档名称、发布日期、原文页码或具体原文片段，人工复核仍需回到管理端查找。

### 两病种需要补充的资源

**脂肪肝：**

- 保留当前已批准标准，并在报告中展示标准文档名称、版本日期和原文定位。
- 为参考病例补充匿名编号、年龄、性别、基线阶段、观察跨度和结局来源。
- 明确区分真实病例、合成病例和规则重组病例。

**AD：**

- 补充量表版本、语言和教育程度等上下文。
- 补充血液或脑脊液样本类型、检测平台和检测方法。
- 在没有经过审核的通用阈值前，继续保持 `evidence-only`，不自动输出数值异常结论。
- 为参考病例补充量表版本和生物标志物检测条件，避免把不同条件的病例直接比较。

### 结论

第 5 项目前是：

```text
标准来源链路已经存在
→ 脂肪肝可以进行有限的正式参考范围判断
→ AD 只能提供证据参考
→ 参考病例目前只是指标重叠筛选
→ 还不是严格的相似病例检索
```

后续正式流程必须保证：

```text
按疾病读取已批准标准
→ 校验标准适用条件
→ 只使用匿名且来源可追溯的参考病例
→ 将标准解释、参考病例和模型预测分别呈现
→ 查询失败时明确标记证据不可用，不伪装成没有证据
```

## 第 6 项：生成完整预测报告

### 目标流程

系统应把病例基本资料、全部访视、数据质量、观察到的变化、模型预测、疾病标准、参考病例和局限性组织成一份可阅读、可追溯的报告。报告必须明确区分观察事实、标准解释和模型结果；模型不可用或数据不足时，应说明具体原因，不能用空值或技术枚举掩盖。

### 当前已经具备

- 报告生成器已经形成 11 个章节。
- 报告区分已观察到的事实、模型风险结果、阶段预测、下一次访视趋势、标准和参考病例、局限性。
- 报告生成后会保存正文 `content`、结构化预测 `prediction_result`、输入快照 `input_snapshot` 和证据来源 `sources`。
- 历史报告读取保存正文，不重新调用模型。
- PDF 使用保存的正文生成，不重新计算预测。
- 前端支持实时生成、报告目录、观察趋势图和 PDF 下载。
- 脂肪肝和 AD 都有对应的报告验收测试。
- 专项验证通过：后端报告、历史、PDF 测试 `20 passed`；前端报告 UI 合约测试 `7 passed`。

### 当前缺失或不符合目标流程的部分

1. **正文中的病例身份信息不完整。** 页面标题显示病例标签和生成时间，但正文没有完整列出报告编号、匿名病例编号、年龄、性别和基线阶段。
2. **数据质量章节过于简单。** 目前主要显示访视次数和指标数量，没有完整列出缺失核心指标、单位冲突、观察次数不足、年龄/性别/阶段缺失和模型输入契约是否满足。
3. **观察事实缺少部分纵向信息。** 当前有首次值、最近值、绝对变化和观察次数，但没有稳定展示百分比变化、每次访视的完整时间序列、检测来源、治疗变化、AD 量表上下文或脂肪肝影像检查类型。
4. **模型结果说明仍不够业务化。** 模型可用时能显示风险分数和模型版本，但没有完整显示校准状态、训练数据构成、合成数据限制、临床有效性声明和本次实际使用的输入字段。
5. **人工复核建议过于通用。** 当前主要提示核对原始病历、单位和标准适用性，没有根据 ALT 单位冲突、AD 缺少量表版本、年龄缺失或模型未参与等具体问题形成结构化复核清单。
6. **脂肪肝和 AD 的报告差异还不够明显。** 脂肪肝可以使用部分正式参考范围；AD 当前只能使用证据参考。报告能够表达这种状态，但病种专属说明还不够清晰。
7. **实时页面和保存正文存在两条显示路径。** 实时生成时前端显示 SSE 拼接内容，完成后再读取数据库正文。当前专项测试已验证最终正文一致，但实时内容和最终版本之间还缺少明确的状态和版本提示。
8. **“内容完整”不等于“临床可用”。** 当前模型和部分参考病例来自合成或规则重组数据。报告可以完整展示工程结果，但不能据此宣称具有临床预测能力。

### 两病种报告边界

**脂肪肝：**

```text
观察数据
→ 部分正式参考范围
→ 模型风险和趋势
→ 报告
→ 历史
→ PDF
```

工程链路基本可运行，但年龄、数据质量、模型临床有效性和人工复核内容仍需补强。

**AD：**

```text
观察数据
→ 证据型标准
→ 工程模型结果或不可用说明
→ 报告
→ 历史
→ PDF
```

报告可以生成，但必须明确：AD 标准目前不能直接给出数值诊断结论；模型结果不能等同于 AD 诊断；量表和生物标志物缺少适用上下文时应降级说明。

### 结论

第 6 项目前是：

```text
报告生成、保存、历史查看和 PDF 已连通
→ 章节结构完整
→ 观察事实、标准证据和模型结果已分开
→ 但病例身份、数据质量、模型说明和人工复核内容还不够完整
→ 脂肪肝可作为工程演示报告
→ AD 不能作为临床判断报告
```

后续正式流程必须保证：

```text
保存完整输入快照和结构化结果
→ 用结构化结果生成正文
→ 明确展示模型、标准和数据的适用边界
→ 历史和 PDF 只使用已保存正文
→ 新模型只影响新生成的报告
```

本项已由用户确认。下一项“保存报告正文、预测结果和输入快照”待用户确认后再开始核查和补充。

## 第 7 项：保存报告正文、预测结果和输入快照

### 目标流程

每次报告生成都应形成一份不可随病例、模型或标准后续变化而改变的历史记录，同时保存：生成时输入、结构化预测、证据来源和最终正文。旧报告不得在打开历史或下载 PDF 时重新计算；新模型只影响之后新生成的报告。

### 当前已经具备

- 报告开始生成前会先保存 `input_snapshot`。
- 输入快照包含病例 ID、疾病 ID 和名称、病例标签、性别、基线阶段、病例备注、按日期排序的全部访视、指标数值和单位、访视备注以及本次模型选项。
- 预测完成后会保存 `content`、`prediction_result`、`sources`，并把状态更新为 `completed`。
- 正常完成时，正文、结构化预测、来源和完成状态在同一次数据库提交中更新。
- 历史报告接口直接读取已保存的正文和结构化结果，不重新调用模型。
- PDF 直接使用已保存的正文和预测结果，不重新计算。
- 病例后续修改或访视被替换后，旧报告正文和输入快照不变。
- 病例被删除后，报告通过自身快照继续保留生成时输入。
- 用户取消生成时，`generating` 报告会变为 `cancelled`。
- 推理过程异常时，报告会变为 `failed`，并保存安全错误代码。
- 专项验证通过：报告持久化、病例快照和 schema 测试 `13 passed`。

### 当前缺失或存在风险的部分

1. **模型加载失败可能留下长期 `generating` 报告。** 当前先创建报告，再加载活动模型；如果模型或 release set 在报告生成器接管前加载失败，初始记录可能无法稳定更新为 `failed`。
2. **输入快照没有独立完整性哈希。** 快照有 schema 版本，但没有快照 SHA-256 或明确生成时间，不能快速验证快照是否被修改，也不能用统一生成标识证明正文、预测和快照属于同一次生成。
3. **输入快照可能保存不安全的病例标签。** `patient_label` 会进入快照；如果操作者误填姓名、住院号或联系方式，这些内容会进入报告和历史数据。目前没有强制匿名格式或敏感信息拦截。
4. **失败报告保留的审计上下文不足。** 推理失败时通常只保存状态和安全错误代码，没有完整保存失败阶段、当时模型组版本、具体输入契约状态和标准来源读取状态。
5. **前端报告列表不能直接展示输入快照摘要。** API 的 `ReportListItem` 已包含 `input_snapshot`，但当前前端侧边栏没有展示；生成时的病例和访视摘要仍需要进入详情后才能查看。
6. **来源存在双份保存。** 来源同时保存在 `AIReport.sources` 和 `prediction_result.evidence.sources`，目前没有数据库级约束保证两份内容始终一致。
7. **快照与模型身份分散在两个字段。** 输入保存在 `input_snapshot`，模型组版本主要保存在 `prediction_result.release_set`；必须同时读取两者才能还原完整的生成上下文。

### 历史报告和新模型的影响边界

当前行为符合以下目标：

```text
旧报告
→ 读取生成时正文、预测、来源和输入快照
→ 不重新调用模型或标准解析
→ 病例修改、标准更新和模型切换都不改写旧报告
```

```text
再次生成报告
→ 读取当前病例快照和当前活动模型
→ 生成新的正文和预测结果
→ 保存为新的报告记录
```

因此，新模型只影响新生成的报告，不会覆盖旧报告。

### 两病种保存边界

**脂肪肝：**

- 正常报告可以同时保存观察数据、参考范围、模型结果和输入快照。
- 历史报告不受后续病例修改影响。
- 后续需要补充年龄、匿名标签和统一的模型组版本记录。

**AD：**

- 可以保存量表和生物标志物输入快照。
- 如果生成时没有量表版本、语言、教育程度、样本类型和检测方法，这些上下文在历史中也会永久缺失。
- 历史报告必须保留生成时的 `evidence-only` 边界，不能因标准或模型更新而重新解释。

### 结论

第 7 项目前是：

```text
正常生成时
→ 输入快照、预测结果、来源和正文一起保存
→ 历史查看和 PDF 不重新计算
→ 新模型只影响新报告
```

后续正式流程还需补齐：

```text
模型加载失败时状态稳定收敛
→ 快照完整性哈希或统一生成标识
→ 病例标签匿名保护
→ 失败阶段和版本审计
→ 两份来源数据的一致性保证
```

本项已由用户确认。下一项“历史查看”待用户确认后再开始核查和补充。

## 第 8 项：历史查看

### 目标流程

操作者应能从历史列表找到已经生成的脂肪肝或 AD 报告，打开后查看生成时保存的正文、结构化预测、证据来源和输入快照。历史报告必须保持生成时的版本和结论，不因病例修改、标准更新或模型切换而重新计算。

### 当前已经具备

- 后端提供报告列表和报告详情接口。
- 报告列表按创建时间倒序排列。
- 只显示当前 AI 操作者自己创建的报告。
- 管理员也不能越权查看其他操作者的报告。
- 非报告所有者访问时统一返回“报告不存在”，不会暴露报告是否存在。
- 可以按 `analysis_type` 过滤，只显示纵向预测报告。
- 历史列表显示生成时间、报告标题和报告状态。
- 点击历史报告后，前端会先清理当前实时生成状态，再加载保存的报告详情。
- 历史详情直接读取数据库中已保存的正文，不重新调用模型、标准解析或参考病例检索。
- 旧版预测结果仍能兼容 `longitudinal_prediction.v1`、`v2` 和 `v3`。
- 旧版报告没有结构化进展信号时，会显示“历史 v1 报告未保存结构化关键信号，未重新计算”。
- 历史报告可以继续下载 PDF。
- 报告删除操作有所有权校验。
- 相关专项验证通过：权限、报告列表和报告状态测试 `34 passed`；前端历史报告 UI 合约测试已覆盖历史加载和旧版本兼容。

### 当前缺失或不符合目标流程的部分

1. **历史列表只加载前 20 条。** 后端支持 `skip` 和 `limit`，但前端只调用一次 `skip=0、limit=20`，没有分页、加载更多或按时间查询；报告超过 20 条后，较早的记录无法从页面继续找到。
2. **历史列表缺少疾病和病例信息。** 左侧主要显示标题和时间，没有明确显示疾病名称、病例匿名编号、基线阶段、访视次数和报告生成时使用的模型组版本；标题相似时不易区分不同脂肪肝或 AD 病例。
3. **历史详情没有专门展示生成时快照摘要。** 数据库保存了 `input_snapshot`，但页面主要展示正文，没有单独清晰地展示生成时病例资料、访视数量和日期范围、指标和单位、模型选项及标准来源。
4. **前端类型没有完整声明 `input_snapshot`。** 后端 `ReportOut` 包含该字段，但前端报告类型没有明确声明，运行时可能拿得到，TypeScript 代码却不能安全使用。
5. **报告列表携带结构化预测结果。** 列表本应是轻量数据，但 `ReportListItem` 仍包含 `prediction_result`；结果较大时会增加请求量，也使列表和详情的数据职责边界不清晰。
6. **失败或生成中的历史记录说明不足。** 列表能显示 `generating`、`failed` 和 `cancelled`；安全错误码保存在数据库/API 中，但当前详情页面不渲染错误码，也缺少操作者能理解的失败阶段，例如模型加载、输入契约、标准来源或推理过程。
7. **病例标签仍可能进入历史标题。** 历史标题由病例标签拼接生成；如果误录姓名、住院号或联系方式，这些信息会长期出现在历史列表和报告标题中。
8. **历史列表没有显式提示固定版本。** 正文和预测结果可能包含模型组版本，但列表没有明显提示“本报告使用生成时模型，不是当前最新模型”，操作者容易误以为打开历史报告会自动显示当前模型重算结果。

### 两病种历史查看边界

**脂肪肝：**

- 历史报告可以保留生成时的观察数据、参考范围、模型结果和 PDF。
- 后续更新脂肪肝模型或标准，不应改变旧报告。

- 如果生成时缺少量表版本、语言、教育程度、样本类型和检测方法，这些缺口会永久保留在历史记录中。

## 第 9 项：下载 PDF

### 目标流程

操作者从已完成的历史报告中下载 PDF。PDF 必须使用报告生成时已经保存的正文、结构化预测和观察序列，不重新调用模型、不重新查询标准，也不能因当前病例或模型变化而改变历史报告内容。

### 当前已经具备

- 只有 `completed` 状态的报告可以下载。
- 下载前会校验报告是否属于当前 AI 操作者。
- 报告不存在、未完成或正文为空时，会安全拒绝下载。
- PDF 使用数据库中保存的 `report.content`。
- PDF 使用保存的 `prediction_result` 生成已观察数据图表。
- 图表只使用至少 3 次有效观察、单位一致且已经保存的观察序列。
- 单位冲突、单位缺失或观察次数不足时，不绘制趋势图，只保留表格。
- PDF 模板包含 A4 页面、中文字体回退、页边距、表格样式、关键区块分页保护、页眉、页脚和页码。
- Markdown 转 HTML 前有标签白名单过滤。
- 下载文件名进行了换行、引号清理和 URL 编码。
- PDF 生成失败时，接口返回安全提示，不泄露本机路径、密码或 traceback。
- PDF 下载次数会记录到 `download_count`。
- 相关专项测试通过：PDF、报告历史、PDF 安全和排版契约共 `24 passed`。

### 当前缺失或存在风险的部分

1. **没有验证真实浏览器环境下的全部中文字体效果。** 代码设置了微软雅黑、宋体和苹方等字体回退，但不同电脑的字体安装情况不同，可能出现中文字体替换、字宽变化或分页差异。
2. **长报告分页仍可能出现视觉问题。** 关键区块已经设置分页保护，但很长的表格、连续列表或多个趋势图仍可能跨页；当前专项测试主要验证 HTML 结构和 CSS 契约，没有覆盖各种真实长报告的逐页视觉验收。
3. **PDF 没有单独显示“生成时模型版本”提示。** 模型组版本可能出现在技术附录，但 PDF 没有在页眉或摘要区域明确提示“本 PDF 使用的是报告生成时的模型版本”。
4. **每次下载都会重新生成 PDF。** PDF 内容使用保存正文，没有重新预测，这是正确的；但每次下载仍会重新执行 Markdown、HTML 和浏览器渲染，没有缓存已生成的 PDF 文件。
5. **PDF 错误只对操作者显示统一提示。** 这符合安全要求，但没有把失败阶段记录到报告的可审计字段中；字体、浏览器、模板或资源问题仍主要依赖后台日志定位。
6. **报告标题仍受病例标签影响。** 下载文件名和 PDF 页眉使用报告标题，而报告标题来自病例标签；如果标签包含姓名、住院号或联系方式，可能长期出现在下载文件名和 PDF 页眉中。
7. **PDF 中的标准来源信息仍不够完整。** 当前可以显示标准版本 ID、规则 ID 和参考范围，但没有稳定展示标准文档名称、发布日期、原文页码或原文片段，人工复核时仍需回到管理端。

### 两病种 PDF 边界

**脂肪肝：**

- 可以生成包含观察趋势、参考范围、模型状态、局限性和人工复核内容的 PDF。
- 单位一致且观察次数足够时，可以绘制 ALT、ALB 等观察趋势图。
- 参考范围判断必须保留标准来源和适用性边界。

**AD：**

- 可以生成包含 MMSE、MoCA、CDR 等观察变化的 PDF。
- AD 标准目前是 `evidence-only`，PDF 不能把量表或生物标志物写成确诊阈值。
- 缺少量表版本、语言、教育程度、样本类型或检测方法时，PDF 应明确显示证据限制。

### 结论

第 9 项目前是：

```text
PDF 下载端点已连通
→ 权限和状态校验存在
→ 使用保存正文生成
→ 历史报告不会重新预测
→ 趋势图只使用已保存且可比较的数据
→ 错误信息不会泄露敏感细节
```

主要需要补齐：

```text
真实浏览器和中文字体验收
→ 长报告逐页视觉验收
→ PDF 显示生成时模型版本
→ 可选 PDF 缓存
→ 失败阶段审计
→ 下载文件名和页眉的匿名保护
→ 标准文档完整溯源
```

### 发现的主要缺口

1. **已完成：`operator_cases` 单独保存年龄。** 已通过 Alembic `0013` 增加可空整数列和 `0–120` 检查约束；新病例必须填写年龄，旧病例保留空值但生成新报告前必须补录。年龄已进入报告输入快照和两条纵向模型特征路径。
2. **仓库实施已完成，生产迁移尚未执行：疾病字典可扩展，AI 操作者只使用许可子集。** 数据库通过 `diseases.code` 保存不可由普通 API 修改的稳定身份，通过 `operator_enabled` 保存管理员控制的操作者许可；后端能力注册表当前只注册 `fatty_liver` 和 `ad`。因此数据库没有把中文疾病名称硬编码进 CHECK，未来仍可增加其他疾病，但新疾病默认停用，只有同时“管理员启用且后端具备对应能力”才能进入操作者流程。操作者疾病接口为只读，直接绕过前端调用病例创建接口时，停用、未知或无程序能力的疾病仍会被后端拒绝；病例创建后也不能修改疾病。疾病停用后，既有病例、历史报告和 PDF 保持可读，但病例、访视和新报告写入被禁止。已被操作者病例、参考病例、报告或标准引用的疾病不能物理删除，数据库限制型外键作为最终保护。
